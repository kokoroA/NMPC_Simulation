# 0910_v7: 推定器も再構築も弁も健全な状態で 3.8 Hz ピッチ発振。旧が飛んだ最大の理由はプロペラ（D90S→GEMFAN）で機体の実効ゲインが約 2 倍になっていたこと

- **日付**: 2026-09-10
- **種別**: investigation | design
- **対象**: `0910_100Hz_v7.csv`、`radio.cpp`(SBUS 0x08)、`control.cpp`(Flight_mode / led_control)、`nmpc_params.hpp`(T_max, R_u)
- **タグ**: #Benzen_NMPC #GEMFAN #D90S #プロペラ #実効ゲイン #ループゲイン #3.8Hz #失速 #SBUS #failsafe #LED #Flight_mode #LOGスイッチ

## 症状（3 件）

1. 100 Hz ログモードで arm すると LED（normal）が点かないことがある。LOG スイッチを OFF→ON で直る。
2. 離陸のためスロットルを上げていると突然モータが止まる。arm/disarm で直る。
3. 同じ条件で飛行し、ロール・ピッチ評価に入ったところで大きく姿勢を崩し墜落。

## 1. LED — `Flight_mode` の更新が LOG スイッチで止まる

`control.cpp:1330/1345`: `Flight_mode = NORMAL / MODE_HOVERING` の代入は **`Chdata[LOG] < 200` が条件**。
LOG スイッチが ON の間はどの分岐にも入らず `Flight_mode` が更新されない。直前に FTC スイッチを触るなどして
`Flight_mode` が `MODE_FTC(2)` のまま残っていると、`led_control()` は `Ftc_mode==0` なので FTC 分岐にも
`NORMAL` 分岐にも入らず**消灯**する。LOG OFF→ON で `NORMAL` が代入されて直る、という報告と一致する。
制御自体は `Flight_mode` に依存しない（NMPC は動く）ので表示だけの問題だが、
**LOG スイッチが飛行モードの判定に混ざっている**のは危険。判定から `Chdata[LOG]` を外すべき。

## 2. モータ停止 — 受信機の SBUS FAILSAFE (0x08)

`t=0.0–3.5 s` の 441 サンプルが `failsafe=6`（`FS_RX_FAILSAFE`）。この間パイロットはスロットルを上げ続け
（`T_ref` 0.53→2.07、`u_base` 1.45 まで）、NMPC 内部 duty は 0.95 で張り付いているが実 PWM は `motor_stop()`。
0x08 は受信機が送信機を見失ったときに**受信機自身が立てるフラグ**（`radio.cpp:152`、`sbus_data[23]`）で、
ファームはそれをラッチし disarm でのみ解除する設計どおりに動いた。
原因は電波リンク。0909/0910 で十数回墜落しており、**受信機アンテナの損傷・送信機電池・距離**を疑う。
これまでの全ログで `rx_flags` 非ゼロは 0 だったので、この日の午後に始まった物理的な変化。

## 3. 墜落 — 推定器・再構築・弁・箱がすべて健全な状態での 3.8 Hz ピッチ発振

v7 の飛行（7.1–12.5 s）は今日初めて**混じり物のない**事例:
推定ドリフト −0.41/+0.78 deg/s（正常）、バイアス状態 ≤0.9 deg/s、`ekf_bias_reset=1`、再構築 9 回（1.4/s）、
`nonfinite=0`、逸脱前は `|λ|=0`・box 非活性・バーストなし、`loop_us` p95 9.4 ms。

破綻: `t=9.5–11.35` に `p,q,tau_x,tau_y` すべてのピークが **3.78 Hz**（q のパワーの 93%、tau_y の 87%）。
`q` の 0.3 s rms は `13 → 13 → 14 → 18 → 27 → 55 deg/s` と単調に成長し、`t=11.5` に `theta` −14.7° で逸脱。
**40–50 ms の実効遅れに対してループゲインが高すぎる、教科書どおりの限界発振。**

## なぜ旧で飛んで今は落ちるか — プロペラで機体の実効ゲインが約 2 倍になっていた

指令トルク → 角加速度の同定（遅れを掃引して最良適合）:

| ログ | プロペラ | roll ゲイン [rad/s²/unit] | pitch | モデル比 (roll / pitch) |
|---|---|---|---|---|
| 0904_v5（飛べた） | **D90S** | **393** (R² 0.34) | **295** | **0.68 / 0.54** |
| 0909_v2 | GEMFAN | 852 | 625 | 1.47 / 1.14 |
| 0910_v1 | GEMFAN | 639 (R² 0.72) | 720 | 1.11 / 1.32 |
| 0910_v4 | GEMFAN | 604 | 708 | 1.04 / 1.29 |

（0904_v2/v4 は 50 Hz ディザで指令が汚れ R² 0.04–0.09、同定不能。旧プロペラの使える点は v5 のみ。）

**旧プロペラでは機体はモデルの 0.54–0.68 倍しか効かず、新プロペラでは 1.0–1.5 倍。約 2 倍。**
遅れは両方とも 40–50 ms で変わらない。

したがって「旧が飛んだ」実効ループゲインは
　コントローラ（バグで ½）× 機体（D90S でモデルの 0.6）≈ 設計値の **0.3 倍**。
今日の設定（R_u=500/Q_p=30、旧と同じコントローラゲイン）× 機体（GEMFAN で 1.2）≈ **旧の 2 倍**。
私は 3 回にわたりコントローラ側のゲインを旧に合わせたが、**合わせるべきは「コントローラ × 機体」のループゲイン**で、
機体側が 2 倍になっていたことを見ていなかった。

v7 の飛行データから直接測ったコントローラゲインは roll K角 0.575e-3 / K率 0.449e-3（R² 0.79）で
ホスト静的値（0.570 / 0.497）と一致 → **コントローラは設計どおり。機体が違う。**

## 判断

- ソルバ修正は原因ではない。今日の全墜落は「EKF の偽の傾き」「バースト（実機のみ、未特定）」
  「プロペラ変更で 2 倍になった機体ゲインに対する未調整」の 3 系統で、v7 は 3 番目の純粋な事例。
- **旧へ戻しても 3 番目は直らない**（旧も同じプロペラで飛べば同じ機体ゲイン。0909_v1 が旧相当で墜落している）。

## 対応（案・未適用）

(a) **旧と同じループゲインに戻す**: 旧の roll ループ ≈ 0.606e-3 × 393 = 0.24。新機体 ~700 に対して K角 ≈ 0.34e-3 →
    ホスト掃引（Q_p=20）から **R_u ≈ 1500**。追従はさらに鈍る。「旧と同じ余裕」に戻すだけで、限界モード自体は残る。
(b) **遅れを埋める**（根治）: モータ一次遅れの予測モデル化、または gyro LPF＋位相進み。
(c) 同定値を `nmpc_params.hpp` へ反映（`T_max` 相当を GEMFAN 実測へ）。ただし R 支配の領域では
    B_model を上げると K も上がるので、単独ではループゲインをさらに上げる。(a) と組で。

パイロットの「旧は飛べた」体感に最短で近づくのは (a)。研究として前に進むのは (b)。

## 検証結果

- v7 全区間の推定器・ソルバ内部状態・failsafe・スペクトル・包絡を確認。
- 8 飛行でプラント同定（遅れ掃引）。旧プロペラの点は 1 つ（0904_v5）で R² 0.34 と弱い。**GEMFAN のベンチ推力曲線の
  接線（0.80 N/unit）と D90S（0.64）の比は 1.25 で、2 倍を全部は説明しない。** 残りは慣性・回転数域の差か同定誤差。
- コード・パラメータ変更なし。

## 次に触る人へ

- ⚠ **ゲイン合わせは「コントローラ」ではなく「コントローラ × 機体」で行う。** 機体側の変更（プロペラ・質量・電池）が
  あったら、まず飛行ログからプラントゲインを測り直す。
- ⚠ 0904 の「飛べた」記録は D90S の記録。GEMFAN で飛べた記録は 1 本も無い。
- ⚠ 受信機アンテナを点検すること。FAILSAFE が空中で立てば即墜落する。
