# 機内 100Hz ログをリングバッファ化し、列を NMPC 用に差し替えた

- **日付**: 2026-09-04
- **種別**: design
- **対象**: `Benzen_NMPC/control.cpp`(logging, log_output), `tools/plot_onboard_log.py`
- **タグ**: #Benzen_NMPC #ログ #Logdata #リングバッファ #墜落解析 #100Hz #log_output

## 背景 / 症状

`0904_v3` の墜落で、破綻の瞬間（t=31.03、誤差 +5° に −1199 deg/s² の逆向き指令）が
**10 Hz の Wi-Fi テレメでは 1 サンプルしか写らず、原因を特定できなかった**。

## 原因 / 判断根拠

**確認済み事実。** 機内 100Hz ロガーは**すでに存在していた**が、そのままでは使えなかった。

- `Logdata[47890]`（187 KB）に `logging()` が `angle_control` から 100 Hz で書く。
  LOG スイッチ（`Chdata[6] > 200`）で開始、スティックコマンドで USB ダンプ。
- **問題1: 列が PID 時代のもの。** `P_com`/`Q_com`/`R_com`（NMPC では未使用）、
  `altitude`/`ideal`/`T_stick`/`input`（未接続で常に 0）が入っている一方、
  **6 発の duty・`iter_us`・`cycles`・`failsafe` が入っていない。**
  今回いちばん見たかった duty が無い。
- **問題2: 「先頭 14.5 秒」しか残らない。** 33 列 × 1451 行 = 14.5 s で満杯になり `Logflag=2` で停止。
  **32 秒の飛行なら離陸直後で埋まり、墜落の瞬間は残らない。**
- **問題3**: スイッチを戻すと `LogdataCounter = 0` で中身を捨てていた。墜落後の吸い出しができない。
- **問題4**: `log_output()` が PID ゲインを出力する（NMPC では無意味）。

## 対応

**リングバッファ化し、列を差し替えた。バッファサイズは変えていない（187 KB のまま）。**

- `DATANUM` 33 → **22**、`LOGROWS = 47890/22 = 2176` 行 = **21.8 秒 @100Hz**
- 満杯後は最古の行を上書きし、**常に直近 21.8 秒を保持**する
- スイッチを戻しても中身を消さない（次に ON にしたときだけ先頭から取り直す）
- 列: `phi,theta,p,q,r / phi_ref,theta_ref,psi_ref / T_ref,u_base /
  u_fr..u_rl / iter_us,loop_us,cycles / failsafe,ftc,acc_norm`
- `log_output()` は最古の行から CSV で出力。ヘッダに `#params`（N, T_max, mass, Ct, CQ, C_QT）と
  `#cost`（Q, R_u, terminal）を印字するので、**後からどの設定で飛んだかログだけで分かる**
- `tools/plot_onboard_log.py` を新規追加（読み込み＋5 段の PNG 出力）

**却下した案**: Wi-Fi テレメを 100 Hz に上げる。
UDP なので**取りこぼしが起きる**（今回のような 1 サンプルの異常は落ちると見えない）。
core0 に 100 Hz の送信負荷が乗り、スナップショットが単一バッファで core0/core1 が競合する。
**墜落解析には機内ログ、飛行中の監視には Wi-Fi、と使い分ける。**

**却下した案**: 列を 16 に削って 30 秒にする。`acc_norm` と `loop_us` を落とすことになり、
衝撃検知と周期の破綻が見えなくなる。**21.8 秒あれば墜落前後は十分に入る。**

## 検証結果

- ビルド成功。`text 675704 → 675352`、`bss 352224 → 352204`。**メモリ増加なし。**
- `DATANUM=22` / `LOGROWS=2176` / 21.8 s / 187.0 KB を算術確認。
- ELF に新しい `#cols: t,phi,...` ヘッダが入っていることを確認。
- `control.cpp` は CRLF。バイナリモードで編集し行末を維持（2751 → 2766 行）。
- `plot_onboard_log.py` をダミーデータで実行し、フェイルセーフ検出と PNG 出力を確認。
- **実機でのダンプは未実施。**

## 次に触る人へ

- ⚠ **バッファは RAM。墜落後にバッテリーを抜くと消える。**
  墜落したら**電源を切る前に**スティックコマンド（スロットル最小＋ラダー左＋エルロン右＋エレベータ上を
  0.5 秒）で `Arm_flag=4` に入れて吸い出すこと。
- ⚠ **墜落後に LOG スイッチを ON→OFF→ON しないこと。** 次の ON で先頭から取り直すため、
  直前のデータが上書きされる。
- **LOG スイッチを入れている間は `Flight_mode` が変わらない。**
  `NORMAL`/`MODE_HOVERING` の判定がどちらも `Chdata[LOG] < 200` を要求するため。
- ダンプ量は 22 列 × 2176 行で約 640 KB。USB CDC で数秒かかる。
- **10 Hz のテレメでは 0.1 秒で起きる破綻は原因が分からない**、というのが今回の教訓。
  リアルタイム系では「最悪ケースを取りこぼさない記録」を先に用意すること。
