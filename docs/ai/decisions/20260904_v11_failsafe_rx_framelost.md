# 空中でのモータ停止は姿勢の脱出条件ではなく SBUS の FRAME_LOST(0x04) 単発ラッチだった

- **日付**: 2026-09-04
- **種別**: bugfix | investigation
- **対象**: `Benzen_NMPC/control.cpp` `failsafe_check()`, `radio.cpp:149`, ログ `tools/0904_v11.csv`
- **タグ**: #Benzen_NMPC #フェイルセーフ #SBUS #FRAME_LOST #FS_RX_LOST #ラッチ #2.4GHz #WiFi干渉 #Q_r #飽和

## 背景 / 症状

`Q_phi=Q_theta=150, Q_p=Q_q=20, Q_r=40` での約 67 s の飛行の最後に、**空中で突然モータが止まった**。
ユーザの見立ては「大きい目標値で一瞬姿勢が崩れて姿勢の脱出条件に触れたのでは。
だとすればしきい値を厳しく（広く）すべきか」。

## 原因 / 判断根拠

**確認済み事実。ユーザの見立ては誤り。**

- テレメトリの `failsafe` 列は最後の 3 サンプルだけ **1 = `FS_RX_LOST`**。
  `3 = FS_ATTITUDE` / `4 = FS_RATE` / `5 = FS_OVERG` は**一度も出ていない**。
- **発動した瞬間の姿勢は φ = +1.5°, θ = −2.6°、角速度は 11.3 / 11.7 / 2.0 deg/s。ほぼ水平・ほぼ静止。**
  飛行中の最大でも `|phi|` 18.6°/60°, `|q|` 55.1/300 deg/s と、**しきい値の 1/3 にも届いていない**。
  発動後に姿勢が乱れているのは**モータが切れて落下した結果**であって原因ではない。

**設計上の欠陥。**

`failsafe_check()` の (1) は `0x08 (FAILSAFE)` と `0x04 (FRAME_LOST)` を **OR で同一視**し、
`Chdata[16]`（`radio.cpp:149` で毎フレーム上書きされる生バイト、カウンタもデバウンスも無し）を
そのまま見て**ラッチ**している。

**SBUS 受信機は 1 フレーム（7–14 ms）取りこぼしただけで 0x04 を立てる。**
これは電波環境が少し混めば日常的に起きる事象であり、「操縦不能」を意味しない。
**単発の 0x04 で空中のモータを永久に切るのは反応が過剰。**
しかも本物のリンク断は (2) `FS_RX_TIMEOUT`（200 ms 無受信）が既に捕まえるので、
0x04 で即停止する必要は最初から無かった。

**傍証（推測を含む）**: Wi-Fi テレメトリの欠測率は 0–60 s で 2–8 % だったのに対し、
**停止直前の 60–70 s だけ 16.1 %** に跳ね上がり、直前には 0.70 s の連続欠測があった。
電波環境の悪化自体は実在した可能性が高く、**0x04 は誤検知ではなかった**かもしれない。
ただし **Pico 2 W の Wi-Fi AP が 2.4 GHz で RC リンクと同帯域**という自己干渉の疑いは**未検証**。

## 対応

**この decision の時点ではコード未変更（分析のみ）。** 提案は
[`docs/20260904_v11_failsafe_rx_lost.md`](../../20260904_v11_failsafe_rx_lost.md)。

1. `0x08` は即ラッチのまま。`0x04` は**単発では発動させない**（連続 N フレーム、または純粋にカウントのみ）。
2. 原因コードを `FS_RX_FAILSAFE` / `FS_RX_FRAMELOST` に**分離する**。
3. テレメトリに `Chdata[16]` の生値と frame-lost 累積カウントを出す。
4. Wi-Fi テレメトリを切って同条件で飛ばし、自己干渉かどうかを切り分ける。

**却下した案（ユーザの当初案）**: 姿勢 60° / 角速度 300 deg/s のしきい値を広げる。
**今回まったく関与していない**うえ、広げると本当に姿勢が破綻したときの保護だけが失われる。

**保留した案**: 受信機ロスト時に全モータ即停止ではなく自動降下させる。
高度を持ったまま切れば必ず墜落するので筋は良いが、設計変更が大きい。まず 1–3 を先に。

## 検証結果

- ログ 626 行を全走査。`failsafe != 0` は末尾 3 サンプルのみ、値はすべて 1。`arm` は全区間 2。
- 脱出条件の余裕: `|phi|` 31.0 %, `|theta|` 20.7 %, `|p|` 31.7 %, `|q|` 18.4 %, `|r|` 26.4 %。
- テレメトリ受信率 93.0 %（626 / 673）。欠測は末尾 10 s に集中（16.1 %）。
- **実機での再現・修正後の確認は未実施。**

### 副次（重み `Q_r = 40` の評価、実測）

- **ヨーは直った**: 追従振幅比 −1.066 → **+1.152**、相関 +0.21 → **+0.80**、
  ドリフト +21 → **+5.2 deg/s**。[`20260904_yaw_qr_not_psiref.md`](20260904_yaw_qr_not_psiref.md) の判断は正しかった。
- **代償**: Δu の yaw 分散比 29.3 % → **41.5 %**、duty 飽和率 1–5 % → **23.2 %**。
  ただしヨーの実指令量 `ΣkS·u` は最大差動の **5.4 %** しか使っておらず、**ヨー軸自体は飽和していない**。
  飽和の主因は `u_base` 平均 0.627 / 最大 0.832（上方向の残り 0.118）＝**推力マージン不足**。
- 飽和はモータ間で偏る: FR 10.0 / RR 9.1 / ML 8.4 / MR 7.1 % に対し **FL 0.7 / RL 0.2 %**。
- `loop` 平均 8.31 ms、10 ms 超過 0.3 %。`N = 14` の効果は維持。

## 次に触る人へ

- **「フェイルセーフが働いた」を姿勢のせいだと決めつけないこと。原因コードを先に読む。**
  今回はログに答えが 1 バイトで書いてあった。
- **原因コードを複数の物理現象に共有させないこと。** `FS_RX_LOST` が 0x04 と 0x08 の
  両方を指していたため、ログだけでは「単発の取りこぼし」か「送信機ロスト」か区別できなかった。
  [`20260901_ftc_mode_and_failsafe.md`](20260901_ftc_mode_and_failsafe.md) で
  「チャンネル番号とモード値に同じマクロを使うな」と書いたのと**同じ種類の失敗**。
- **保護の追加は「発動したときに何が起きるか」まで含めて設計すること。**
  空中での全モータ即停止は保護ではなく墜落である。
- `OverG_flag` は `control.cpp:2301` で立ち `control.cpp:701` の 1 か所でしか落ちない。
  しきい値 150 m/s² を下げるときはクリア条件も対で見直す。
- 未解決の持ち越し: `mass = 0.35` vs 実測 ≈0.383 kg、`T_max = 1.04` vs 同定値 0.79–0.82、
  `Iz = 3.00e-3` の出所、RL モータの Δu 分散偏り。
