# 飛べていたのは 50 Hz ディザで実効ループゲインが半分以下だったから。ゲイン合わせの基準を間違えていた

- **日付**: 2026-09-10
- **種別**: bugfix | investigation
- **対象**: `nmpc_params.hpp`(cost::R_u)、`0904_100Hz_v5.csv`, `0909_100Hz_v2.csv`, `0910_100Hz_v1/v2/v3.csv`
- **タグ**: #Benzen_NMPC #ADMM #チャタリング #ディザ #ループゲイン #R_u #測定方法 #墜落

## 背景 / 症状

`Q_p=Q_q` を 20 でも 10 でも飛行後に墜落する。ユーザから
「0904_100Hz_v5 / 0909_v1 / 0909_v2 では飛べていた。大きい変更点は ADMM のところ」と指摘された。
ソルバ修正のたびに指標（`lambda_reset`, `nonfinite`, `loop_us`, ラグ 1 自己相関）は改善しているのに
実機は飛ばなくなる、という状態が 3 回続いていた。

## 原因: 指令の「大きさ」で合わせたが、合わせるべきは「状態と相関している成分」だった

**確認済み事実。**

各飛行の自由飛行に近い区間で、指令トルクが状態
`[phi, theta, p, q, r, phi_ref, theta_ref, psi_ref, 1]` の線形結合でどれだけ説明できるか（R²）と、
1 サンプルあたりの指令の跳びを測った。

| ログ | R² (roll/pitch/yaw) | 指令跳び 中央値 | 跳び / 状態変化 |
|---|---|---|---|
| **0904_v5 旧ソルバ R_u=120（飛べた）** | **0.20 / 0.31 / 0.14** | **0.3976** | **4.93** |
| 0909_v2 逆算 c R_u=320 | 0.74 / 0.54 / 0.60 | 0.0222 | 0.29 |
| 0910_v1 直接 c R_u=320 Q_p=20 | 0.78 / 0.58 / 0.64 | 0.0231 | 0.29 |
| 0910_v2 直接 c Q_p=1 | 0.83 / 0.81 / 0.87 | 0.0074 | 0.15 |
| 0910_v3 直接 c Q_p=10 | 0.79 / 0.76 / 0.56 | 0.0166 | 0.21 |

**飛べていた 0904_v5 は、指令が毎サンプル 0.40 も跳ぶ 50 Hz ディザ状態で飛んでいた。**
指令トルクのうち状態で説明できるのは roll 20% / pitch 31% / yaw 14% しかない。
モータは τ≈50 ms なので 50 Hz 成分には追従できず、機械的に平均されて消える。
**つまり当時の姿勢フィードバックは、指令の見かけの大きさに対して実質 2-3 割しか効いていなかった。**

`R_u = 320` は「姿勢誤差 8.6 deg に対する実効 \|Δu\| を 0904_v5 の 0.0166 に合わせる」として決めた。
**この \|Δu\| の大半が、効かないディザだった。** ADMM を直してディザが消えた後は、
同じ \|Δu\| が丸ごとトルクになる。合わせるべき量を間違えていた。

**正しい基準は「状態と整合した指令トルク / 姿勢誤差 1 deg」。** 実機実測
（|error| 2-10 deg, |rate| < 30 deg/s のサンプル）:

| ログ | roll | pitch |
|---|---|---|
| **0904_v5（飛べた）** | **0.00050** | **0.00037** |
| 0909_v2（12.35 s で破綻） | 0.00109 | 0.00103 |
| 0910_v1（発振して墜落） | 0.00078 | -0.00027 |
| 0910_v2（Q_p=1、離陸せず） | 0.00134 | 0.00187 |

**飛べた設定に対して 1.6〜2.7 倍のループゲインで飛ばしていた。**
`0910_v3`（Q_p=10）の破綻も、`t=13.53` から実際のロール（ジャイロが見ている）に対して
修正が 40-50 ms 遅れて届き、`t=13.83` で行き過ぎて反転、`t=13.90` に box 隅（`MR=0.001, ML=0.950`）
へ飽和して発散、という**遅れ + 過大ゲインの典型**である。反転周期は約 0.12 s ≈ 4 Hz で、
既知の 4 Hz モードと一致する。

## 対応

`R_u` を 320 → **800**。`Q_p = Q_q = 20` は据え置き（ユーザが 20 へ戻した状態）。

ホスト実測（roll 誤差のみ・角速度ゼロ、Q_p=20、指令トルク / 誤差 1 deg）:

| `R_u` | 320 | 450 | 600 | **800** | 1100 | 1500 |
|---|---|---|---|---|---|---|
| 整合ゲイン | 0.00086 | 0.00071 | 0.00060 | **0.00050** | 0.00040 | 0.00033 |

**`R_u = 800` が 0904_v5 の 0.00050 に一致する。**
ホストの `R_u=320` の値 0.00086 が実機 0910_v1 の 0.00078 と 10% で一致しており、
測定系そのものが実機と整合していることも確認できた。

**採用しなかった案。**

- `Q_p/Q_q` を下げる → [`20260910_qp_reduction_was_a_gain_increase.md`](20260910_qp_reduction_was_a_gain_increase.md) の通り逆効果。
- ADMM 修正を巻き戻してディザを復活させる → ディザは推力を無駄にし、NaN 固着と
  U_lin 発散の温床でもあった。**「安定化に効いていたのはディザではなくゲインの低さ」**なので、
  ゲインを正しく下げれば同じ安定性が得られる。意図的なディザを入れる理由がない。
- `Q_p=10` のまま `R_u=1000` で合わせる → 一致点は 0.00052 で妥当だが、
  0904_v5 は `Q_p=20` で飛んでいる。1 回に 1 つだけ変える。

## 検証結果

- 実機に焼くソースそのものをホストでビルドし、整合ゲイン **0.00050**（8.6 deg）/ **0.00049**（3 deg）を確認。
- ロール 5 deg 初期偏差の応答: モータ 50 ms 遅れ + 純遅延 1-3 周期 + 効き 1.0-1.5 倍のすべてで収束。
- `cmake --build build_fresh` 成功。`text 677784 / bss 352560`。CRLF 混入なし。
- **実機飛行は未検証。** ホストは 4 Hz モードを再現できていないため、
  「ホストで収束した」ことは安全性の保証にならない。

## 次に触る人へ

- ⚠ **ゲインを合わせるときは「指令の大きさ」ではなく「状態と相関している成分の大きさ」を見る。**
  この一件は、無相関なディザが指令の 7-8 割を占めていたために、
  同じ \|Δu\| でも実効ゲインが 2 倍以上違っていた。
- ⚠ 4 Hz モード自体は未解決のまま（[`20260910_residual_4hz_mode_is_the_real_blocker.md`](20260910_residual_4hz_mode_is_the_real_blocker.md)）。
  `R_u=800` はゲインを飛べていた水準へ戻すだけで、位相余裕を作るものではない。
  根治は依然としてモータ一次遅れの予測モデル化。
- ⚠ 0910_v2 2 回目で見つかった EKF バイアス発散は未解決。飛行ごとに
  `(phi の変化) − Σp·dt` を確認すること。
