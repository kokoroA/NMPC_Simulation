# `|U_lin|` ガードを実装。積分は v10 に対して純損失だったので、v10 へ戻して耐故障制御へ進む

- **日付**: 2026-09-11
- **種別**: design | bugfix
- **対象**: `Benzen_NMPC/nmpc.cpp`(安全弁 3), `nmpc.hpp`, `nmpc_params.hpp`(ulin_max), `control.cpp`(ログヘッダ)
- **タグ**: #Benzen_NMPC #U_lin #ガード #ADMM #発散 #積分作用 #FTC #耐故障制御 #方針

## 背景 / 症状

ユーザの問い: **「体感は v10（`Q_phi=1000`/`Q_p=80`/`R_u=620`、積分なし）が一番飛ばしやすかった。
積分を削除して耐故障制御に進むべきか、積分を深掘りするか迷っている。」**

## 原因 / 判断根拠

### (1) v10 が最良なのは体感だけでなく全指標でそう（確認済み）

| | roll 相関/振幅比 | pitch 相関/振幅比 | 水平保持 r/p | `ulin` p99/最大 | `lam>1` | `box≥4` |
|---|---|---|---|---|---|---|
| v6 (Q_phi500) | 0.45 / 1.56 | 0.45 / 1.00 | 3.01 / 2.70 | 0.45 / 0.80 | 0 | 0 |
| **v10 (Q_phi1000, 積分なし)** | **0.46 / 1.22** | **0.47 / 0.89** | **2.82 / 2.19** | 0.62 / 2.17 | 8 | **0** |
| v11 (同じ重み + 積分) | 0.46 / 1.44 | **0.29 / 1.69** | 3.48 / **10.44** | 1.08 / 4.08 | 14 | 1 |
| v12 (積分+リーク, R800) | −0.03 / 19.01 | 0.44 / 1.72 | 24.72 / 3.35 | 3.47 / 6.09 | 135 | 108 |

**振幅比が 1.0 に最も近く（1.22 / 0.89）、水平保持も最小（2.82 / 2.19）で、`box≥4` はゼロ。**

⚠ **前回の v11 の評価を訂正する。** v11 を v6 と比べて「ロールは改善」と書いたが、
重みが違う便との比較だった。**同じ重みの v10 と比べると v11 は全指標で悪い**:
ピッチ相関 0.47→0.29、ピッチ振幅比 0.89→1.69、ピッチ水平保持 2.19→10.44 deg。
**積分は追従を良くしていない。ソルバ健全性も落としている（`ulin` 最大 2.17→4.08）。**

### (2) 積分が直そうとしたものは、積分では直せない

外乱は**速度比例（ブローバック）**であり、一定の傾きを保てば必要なトリムは増え続ける。
有限のトリムでは原理的に消せない（[`20260911_attitude_integral_trim_via_xref_shift.md`](20260911_attitude_integral_trim_via_xref_shift.md) に実測と物理の両方を記録済み）。
実際 v11 では上限に張り付き、リークを入れた v12 では墜落した。
**投資に対して返ってくるものが無い領域である。**

### (3) ⚠ `|U_lin|` ガードは、どちらの道を選んでも必要 — とくに FTC では必須

耐故障制御は `Motor_eta` で **box を縮める**ことで故障を表現する（`repository_rules.md` §3）。
つまり **FTC は設計上わざと box を張り付かせる。**
そして 0911_v12 が示したのは、**box が有効になったところからソルバが発散する**という事実
（`box≥4` が 0/0/1 → 108 サンプル、`ulin` 6.09、2.5 deg の誤差にフルの機首上げ）。

**ガード無しで片発停止をやるのは、最も発散しやすい条件へ意図的に踏み込むことになる。**

## 対応

### 実装: 安全弁 3（`|U_lin|` の暴走検知）

`nmpc.cpp` の ADMM 後段、既存の「安全弁 1（lambda 上限）」「安全弁 2（非有限）」の直後に追加。
`ws.z`（次周期の `U_lin`）のノルムが `ulin_max` を **`ulin_max_run` 周期連続**で超えたら、
`ws.U/z/lambda` をゼロにして warm-start を捨て、次周期フル再構築を要求する。

**しきい値は実飛行 6 便の分位点から決めた。** `|U_lin|>1.0` が連続した最大周期数:

| v6 | v4 | v10 | v9 | v11 | **v12（墜落）** |
|---|---|---|---|---|---|
| 0 | 3 | 3 | 5 | 11 | **71** |

→ **`ulin_max = 1.0`、`ulin_max_run = 5`（50 ms）**。
- 健全便（v6 / v10）で**誤発火ゼロ**
- v12 では **t=19.78 に発火**。`q` が跳ねる 19.86 の **0.08 秒前**に捕まえられる
- 単発スパイクは健全便でも起きる（v10 で 3 周期連続）ので**連続回数で見る**のが要点

ログヘッダに `ulin_reset=` を追加（`#solver:` 行）。`lambda_reset` と並べて読める。

### 方針の推奨: v10 へ戻して耐故障制御へ進む

1. データ上 v10 が最良で、**積分は純損失**（上表）。
2. 積分が狙った外乱は**積分では消せない**（速度比例）。深掘りの期待値が低い。
3. `repository_rules.md` §5 の未解決リストは 1. 制御周期、2. 健全飛行の安定化、3. **片発故障飛行**、4. FDI。
   **v10 は 2 を「片発をやってみられる」水準には達している。** 完成目標は 2026 年 9〜10 月。
4. ガードが入ったことで、FTC の box 張り付き条件に踏み込む準備ができた。

## 検証結果

- ビルド **警告・エラー ゼロ**。`text 683560 / bss 422404`。
- ホストのクローズドループ（外乱 0/50/100、機体効き 0.7/2.0/3.0 倍、ヨー外乱 46）で
  **ガード追加前と全数値が一致** ＝ 健全域では発火せず挙動を変えない。
- しきい値の誤発火検証は実飛行 6 便のログで実施（上表）。
- **実機では未検証。**

## 次に触る人へ

- ⚠ **現在のソースは v12 の設定（`R_u=800` + 積分 `enable=1`）のまま。このまま飛ばさないこと。**
  v10 へ戻すのは 2 行:
  - `nmpc_params.hpp` の `R_u` 800 → **620**
  - `namespace trim` の `enable` 1 → **0**
  積分のコードは残してある（`enable=0` でリセットも走る）ので、後で再開できる。
- **FTC の初回は、まず健全飛行で `ulin_reset=0` を確認してから**片発を落とすこと。
  健全飛行で発火するなら、その時点で FTC に進んではいけない。
- ⚠ **v10 も安全ではない**（`ulin` 最大 2.17、`lam>1` 8 サンプル）。同じ崖の上にいて、
  縁から少し遠いだけである。ガードはそのための保険。
- 積分を再開するなら、**まず「速度比例の外乱」をモデルに入れる**方が筋が良い
  （姿勢 5 次元を崩さずに済む形があるかは未検討）。積分の係数いじりは 3 便やって進展がなかった。
