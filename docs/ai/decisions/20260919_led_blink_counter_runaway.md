# 真因は `led_control()` の点滅カウンタ `cnt` が全分岐で共有され、周期より大きい値のまま別分岐に入ると二度と折り返せなくなること

- **日付**: 2026-09-19
- **種別**: bugfix
- **対象**: `Benzen_NMPC/control.cpp`(`led_control`), `tools/0919_v4.txt`
- **タグ**: #Benzen_NMPC #LED #WS2812 #led_control #Arm_flag #点滅 #カウンタ #オーバーフロー #状態共有

## 背景 / 症状

ユーザー報告:

> 何回もarm,disarmやLOGスイッチON、LOG吸い出しなどを試していたら、また同じバグ
> (モードに応じてLEDが光らない、このログはUSB給電だが、バッテリー給電でもおそらく
> この状態ではモーターは回らない)が起きました。おそらく145000ごろからです。

`0919_v4.txt` は USB デバッグ出力が正常に動いた初のログ（`#dbg` 1009 行、168 秒）。
ログ吸い出しの連続再発は起きておらず、[`20260919_log_dump_relatches_forever_and_traps_main.md`](20260919_log_dump_relatches_forever_and_traps_main.md)
のエッジ化修正は効いている。**別の原因が残っていた。**

## 原因 / 判断根拠

### 機構（ソースから確定）

`led_control()` の点滅カウンタは **関数スコープの `static uint16_t cnt` 1 個を全分岐で共有**していた。
各分岐の折り返しは **完全一致**:

| 分岐 | 周期 | 点灯 | 消灯 |
|---|---|---|---|
| 2 ベンチ | `cnt == 40` | 0 | 20 |
| 3 離陸ゲート赤 | `cnt == 80` | 0 | 40 |
| 4 FTC / 6 ホバー / 7 ディスアーム緑 | `cnt == 100` | 0 | 50/50 |

⚠ **自分の周期より大きい `cnt` を持ったまま別の分岐に入ると、`cnt == <周期>` が二度と成立しない。**
`cnt` は 65535 まで増え続け、その間 `cnt == 0` も `cnt == 40/50` も来ないので
**WS2812 に一度も書かれない = LED が直前の色のまま凍る。**

さらに **`cnt` が 100 を超えた時点で点滅する分岐は全部死ぬ。**
以後 LED を書くのは**無条件**の `rgbled_wait()` と `rgbled_normal()` だけになる。
→ **アームして離陸ゲートが開くと normal 色が焼き付き、ディスアームしてもその色のまま。**
これがユーザーが最初に報告した「飛行モードの時の色のまま」そのもの。

**踏む条件**: 周期 100 の分岐（4/6/7）から周期 80 の分岐 3 へ、`cnt ∈ [80,99]` で遷移すること。
⚠ この窓は**ディスアーム点滅の「消灯」半周期（cnt 50..99）の中にすっぽり入る**ので、
**踏んだ瞬間の LED は必ず消灯**になる。ユーザー報告の「LED の色が消えたり」と一致する。
**ディスアーム(7) → アーム(3) は毎回これを引く。確率は 20%（cnt = 80..99 の 20 通り）。**
⚠ **アーム/ディスアームを繰り返すほど必ず踏む。** ユーザーの「何回も試していたら再発」と一致。

### 実測ログからの再現（0919_v4.txt）

`#dbg` は離散状態のエッジで必ず 1 行出るので、`led` 分岐の遷移時刻が ms 精度で取れる。
そこから `cnt` を 400 Hz で再現した結果:

```
  82801 ms  分岐 7(周期100, cnt=93) → 分岐 3(周期80) へ遷移  ← ここで暴走開始
  cnt: 93 → 452 → 1380 → 2379 → … → 31187 (ログ終端)
```

**LED が一度も更新されなかった区間**（終了理由が "unconditional write" = 無条件の normal/wait 書き込み）:

| 区間 [ms] | 長さ |
|---|---|
| 82801 → 88518 | 5.7 s |
| 92652 → 104278 | 11.6 s |
| 111920 → 127246 | 15.3 s |
| **139053 → 157953** | **18.9 s** |
| **160770 → ログ終端** | **20.6 s** |

⚠ ユーザーの体感「145000 ごろから」は 139053→157953 の 18.9 秒の暗転区間に入る。

⚠ **再現の限界**: `cnt` の初期値は 0 と仮定し、遷移時刻はサンプル時刻（main の poll）なので
1 遷移あたり ±1 tick 程度の誤差が乗る。**暴走の開始時刻 82801 ms は概算。**
ただし一度 `cnt > 100` になれば以後すべての点滅分岐が死ぬことは誤差に依存しない。

### ⚠ モータが回らない件との関係（推測を含む）

`0919_v4.txt` は USB 給電でスロットル最小（`cd=0.000`）なので**モータ出力は評価できない**。
ただし `out` 列を見ると、後半のアームの多くが `out=2`（離陸ゲート閉）のまま
2.5 秒経たずにディスアームされている。
**LED が凍ると赤 5Hz 点滅（= ゲート閉 = モータが回らない状態）の表示が出ないので、
ゲートが開いたかどうかを知る手段が無い。** スロットルを上げても回らず、
さらに上げたところでゲートが開いて急回転する、という報告と整合する。
⚠ **この因果は未確認（推測）。** ゲート機構そのものは
[`20260919_disarm_led_freeze_is_armflag4_and_gate_open_throttle_jump.md`](20260919_disarm_led_freeze_is_armflag4_and_gate_open_throttle_jump.md) の別件。

### ⚠ 過去の診断の訂正

[`20260911_v7_arm_gate_recountdown_and_led_unhandled_states.md`](20260911_v7_arm_gate_recountdown_and_led_unhandled_states.md) と
[`20260919_disarm_led_freeze_is_armflag4_and_gate_open_throttle_jump.md`](20260919_disarm_led_freeze_is_armflag4_and_gate_open_throttle_jump.md) は
**「`led_control()` に `else` が無く、未処理状態は `Arm_flag == 4` だけ」**と結論していた。
`else` が無いこと自体は事実だが、**`Arm_flag == 4` は主因ではなかった。**
state 4 は自前で `rgbled_switch()` を 1 秒周期で叩くので「飛行色のまま固まる」を説明できない。
**主因は `cnt` の暴走で、こちらは分岐に当たっていても LED を書かない。**
⚠ **「どの分岐に入ったか」を観測しても足りず、「WS2812 に書いたか」を見る必要があった。**

## 対応

2 段の修正:

1. **分岐が変わったら `cnt = 0`**（`LED_BRANCH(n)` マクロ）。位相も揃うので、
   モードが変わった瞬間に必ず点灯から始まる。
2. **折り返しを `cnt == N` → `cnt >= N`**。万一 `cnt` が大きくても 1 tick で復帰する保険。

**採用しなかった案**: 分岐ごとに別の `static` カウンタを持つ。
変数が 5 個に増えるうえ、モード切替時の位相が揃わない問題が残る。

**今回も入れなかったもの**: `else` に異常色を割り当てる（今は観測専用で `LED_BRANCH(0)` のみ）。
`Arm_flag == 4` は自前で LED を叩くので、枝を足しても上書きされる。
