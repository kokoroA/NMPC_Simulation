# フェイルセーフ: 受信機条件を 0x08/0x04 に分離しデバウンス、解除処理を 400Hz 分岐の前へ移した

- **日付**: 2026-09-04
- **種別**: bugfix | design
- **対象**: `Benzen_NMPC/` control.{cpp,hpp}, radio.{cpp,hpp}, wifi_telemetry.hpp,
  tools/nmpc_udp_client.py, tools/nmpc_udp_client.md, tools/plot_onboard_log.py
- **タグ**: #Benzen_NMPC #フェイルセーフ #SBUS #FRAME_LOST #FS_RX_FRAMELOST #ラッチ #デッドコード #テレメトリ #ver5

## 背景 / 症状

[`20260904_v11_failsafe_rx_framelost.md`](20260904_v11_failsafe_rx_framelost.md) で、
空中でのモータ停止が **SBUS `FRAME_LOST(0x04)` の単発ラッチ**だったと特定した。その修正。

加えてユーザから **「一度フェイルセーフに入ると解除できない」** という別のバグの報告があった。

## 原因 / 判断根拠

**確認済み事実（解除できないバグ）。**

`failsafe_check()` の中に「`Arm_flag != 2` なら解除」が書いてあったが、
**この関数は `loop_400Hz()` の `else if (Arm_flag == 2)` の枝の中からしか呼ばれない**。
つまり `Arm_flag != 2` のときは関数自体が呼ばれず、**解除処理はデッドコードだった**。
`Arm_flag == 3` の枝は `OverG_flag = 0` だけを落としており、`Failsafe_flag` は残る。
結果、一度成立すると**再アームしてもモータが二度と回らなかった**。

「解除条件をその条件が成立しない場所に置いた」という配置の誤り。
[`20260901_ftc_mode_and_failsafe.md`](20260901_ftc_mode_and_failsafe.md) で
`Chdata[16]` が「grep すると存在するので実装済みに見えるが参照が無かった」と書いたのと同型の失敗で、
**今回は「呼ばれない場所にあった」という別の形の不到達コード**である。

**確認済み事実（受信機条件）。**

- SBUS 受信機は **1 フレーム（7–14 ms）取りこぼしただけで `0x04` を立てる**。日常的な事象。
- 本物のリンク断は `FS_RX_TIMEOUT`（200 ms 無受信）が別途捕まえる。
  **`0x04` で即停止する必要は最初から無かった。**
- `0x08` は「受信機が送信機を見失った」という本物の信号で、これは即発動してよい。
- 旧 `FS_RX_LOST = 1` は両方を指していたため、**ログから区別できず原因特定を遅らせた**。

## 対応

**① 受信機条件のデバウンス。** `0x08` は即発動、`0x04` は**連続 16 フレーム**立ち続けたときのみ発動。
16 は SBUS 周期 7–14 ms に対して約 112–224 ms 相当。数えるのは **`radio.cpp` のフレーム完結時**。
400 Hz 側で数えると 1 フレームを複数回数えてしまうため、必ずフレーム単位で数える。

**② 原因コードの分離。** `FS_RX_FAILSAFE = 6`（0x08）/ `FS_RX_FRAMELOST = 7`（0x04 連続）を新設。
旧 `FS_RX_LOST = 1` は**番号だけ残して使用禁止**にした（過去ログを読み替えられなくしないため）。

**③ 計装。** `Rx_sbus_flags`（生値）/ `Rx_framelost_run`（連続数）/ `Rx_framelost_count`（累積）を
テレメトリと USB シリアル CSV の両方へ出した。`NmpcTelPkt` は**末尾に追加**したので
**既存フィールドのオフセットは不変**（188 → 196 B、`NMPC_UDP_VER` 4 → 5）。

**④ 解除の移動。** `loop_400Hz()` の `Arm_flag` 分岐の**前**で解除する。
`failsafe_check()` 側の解除は「呼ばれないので置いても無駄」というコメントに置き換えた。
併せて `Rx_framelost_run` も 0 に戻す（リンクが死んだまま再アームしても即発動しないように）。

**却下した案**: `0x04` を完全に無視する。`FS_RX_TIMEOUT` があるので実害は小さいが、
「フレームは届いているのに中身が失われ続ける」状態を拾えなくなる。連続数で見れば両立する。

**却下した案**: `Arm_flag == 3` の枝に解除を足す。`Arm_flag` は 0/1/3/4 を取りうるので、
枝ごとに書くと**また 1 つ書き忘れる**。分岐の前に 1 か所置くのが正しい。

**却下した案**: `_pad` のように既存フィールドの間に挿入する。既存オフセットが動き、
過去ログ解析と版ずれの事故が増える。末尾追加なら差分が読みやすい。

**保留**: 受信機ロスト時に全モータ即停止ではなく自動降下させる案（設計変更が大きい）。
100 Hz オンボードログの列追加（`DATANUM` を増やすと記録可能秒数が 21.8 s から減る）。

## 検証結果

- **ビルド成功**（`build_fresh`）。`text 675608 / bss 352212`（2026-09-01 の 675720 / 352224 から微減）。
- `static_assert` を実フラグ（`arm-none-eabi-g++ -mcpu=cortex-m33`）で通した:
  `sizeof(NmpcTelPkt) == 196`、`offsetof(ftc)==14` / `failsafe==15` / `cycles_since_reset==16` /
  `terminal_scale==184`（**既存オフセット不変**）、`rx_flags==188` / `rx_framelost_run==189` /
  `rx_framelost_cnt==192`、`NMPC_UDP_VER == 5`。
- **ホストで C++ 構造体に既知値を詰めて 196 B を吐き、`nmpc_udp_client.py` の `parse_tel()` で
  読み戻して全フィールド一致を確認した**（フォーマット文字列同士の突き合わせではない実物の照合）。
- `#cols` 文字列（C++）と `NMPC_BENCH_CSV_COLS`（Python）を機械的に比較し、**49 列で完全一致**。
- `FS_RX_LOST` への代入が 1 か所も残っていないことを確認。
- 全編集ファイルの改行コード（CRLF/LF）が編集前後で不変であることを確認。
- **実機での動作確認は未実施。** frame-lost 連続 16 本という値も**実測に基づいていない**。
  次の飛行の `rx_fl_cnt` / `rx_fl_run` の分布を見てから決めること。

## 次に触る人へ

- **「解除条件」は、その条件が成立する場所から到達できるかを必ず確認すること。**
  今回は解除処理が `Arm_flag==2` の枝の中にあり、`Arm_flag != 2` では実行されなかった。
  条件分岐の中に「その分岐が偽のときの処理」を書かない。
- **状態を分岐ごとにクリアしない。** 分岐の前で 1 回だけクリアする。枝が増えるたびに漏れる。
- `rx_flags` / `rx_fl_run` / `rx_fl_cnt` が次の飛行で取れる。
  **`FS_FRAMELOST_RUN_LIMIT = 16` はこの実測を見てから決め直すこと。**
- **Wi-Fi テレメトリを切って同条件で飛ばす切り分けがまだ済んでいない。**
  Pico 2 W の AP は 2.4 GHz で RC リンクと同帯域であり、自己干渉の疑いは未検証のまま。
- ファームとクライアントの `NMPC_UDP_VER` は 5 で揃えた。**どちらか片方だけ焼くと列がずれる。**
