# 外部知能（3 層記憶）と自動運用スキルの構築

- **日付**: 2026-08-20
- **種別**: design
- **対象**: `skills.md`, `docs/ai/`, `.clinerules`, `.cursorrules`, `CLAUDE.md`
- **タグ**: #meta #memory #workflow #cache #setup #skills

## 背景 / 症状

AI アシスタントはセッションが切れると、前回のバグ原因・却下した設計案・調整済みパラメータの根拠を
すべて失う。本リポジトリは NMPC のパラメータと設計判断（PKG-A〜F、E1〜E8 など）が積み重なっており、
「なぜこの値なのか」を毎回 `memo/研究面談/` から読み直すのは高コストで、読み落としも起きる。

一方で、すべての経緯を常時読み込みのルールファイルに詰め込むと、ファイルが単調増加して
毎セッションのコンテキスト（およびプロンプトキャッシュ）を圧迫する。

## 原因 / 判断根拠

「常時参照する知識」と「必要時に引く知識」を同じ場所に置いていたことが問題だと判断した。
両者は更新頻度もサイズの増え方も違うため、物理的に分離する。

- 常時参照＝サイズ固定でなければならない（キャッシュを効かせるため）
- 過去ログ＝単調増加してよい（引く時だけコストを払うため）

## 対応

以下の 3 層構造を構築した。

| 層 | 実体 | 参照方法 |
|---|---|---|
| Repository | `docs/ai/repository_rules.md` | 常時・全文 |
| Archive | `docs/ai/decisions/YYYYMMDD_概要.md` | grep で検索 |
| Global 昇格候補 | `docs/ai/global_drafts.md` | 汎用教訓を発見した時 |

これを人手の運用に頼らず回すため、AI 自身の手順書 `skills.md` に
**開始時（検索）→ 実行 → 完了時（記録）→ 昇格** のルーチンを明文化した。

`repository_rules.md` の初期内容は、`README.md` / `platformio.ini` /
`program/NMPC_simulation/nmpc_simulation.py`（Params, sanity_checks, クラス構成）/
`memo/研究メモ/` / `memo/研究面談/6_9.md`（最新の進捗報告）を読んだ結果から構成した。

### 採用しなかった案

- **すべてを `CLAUDE.md` に集約する**: 実装が進むほど肥大し、常時コストが増え続けるため却下。
  入口はポインタのみとし、実体を `docs/ai/` に置いた。
- **`.clinerules` / `.cursorrules` に同内容をコピーする**: 3 ファイルの二重・三重管理になり、
  片方だけ古くなる事故が確実に起きるため却下。**シンボリックリンク**で実体を 1 つに統一した。
- **decisions を 1 ファイルの追記ログにする**: 検索単位が粗くなり、部分読み込みができない。
  1 判断 1 ファイルにして grep のヒット単位＝読み込み単位を揃えた。

## 検証結果

構築物の存在と参照関係を確認した。

```bash
ls -R docs/ai && ls -l .clinerules .cursorrules
```

- `.clinerules` / `.cursorrules` → `docs/ai/repository_rules.md` のリンク解決を確認（`head` で同一内容が読めること）。
- **開始時ルーチンの動作確認**: `grep -ril "ADMM" docs/ai/decisions/` が本ファイルをヒットすること。
- **完了時ルーチンの動作確認**: 本ファイル自身が、この基盤構築という作業に対する最初の記録である
  （`skills.md` §2 のトリガー「設計判断を下した」に該当）。
- **昇格ルーチンの動作確認**: 本作業から得られた汎用教訓 5 件を `docs/ai/global_drafts.md` に昇格済み。

以上により、検索 → 実行 → 記録 → 昇格の一周がファイル上で成立していることを確認した。

**未検証**: Cline / Cursor 実機でのシンボリックリンク読み込みは確認していない
（macOS の FS レベルでは解決されるが、ツール側が実体を辿るかは未確認）。
Windows へリポジトリを展開した場合はリンクが壊れる可能性がある。

## 次に触る人へ

- `repository_rules.md` が 3,000 文字を大きく超え始めたら、それは Archive へ追い出すべき詳細が
  混ざっているサイン。§5「現在の到達点」以外は安易に増やさない。
- §5 は**上書き更新**する唯一の節。進捗が動いたら古い記述を残さない。
- 記録は「なぜ」だけを書く。何を変えたかは git diff が持っている。
- 最初の実運用（Pico 2 移植、FDI 推定器の実装）でこのルーチンが回るかどうかが本当の検証になる。
  回らなかった手順は `skills.md` ごと直し、その理由を新しい decision に残すこと。
