# ディスアーム後に LED が固まる件：`led_control()` に `else` が無く `Arm_flag==4` が未処理。急回転は離陸ゲートが開く瞬間

- **日付**: 2026-09-19
- **種別**: investigation
- **対象**: `Benzen_NMPC/control.cpp`（`led_control` / `loop_400Hz` の状態機械 / `logdata_out_com`）
- **タグ**: #LED #Arm_flag #LockMode #arm_gate #logdata_out_com #安全 #未修正バグ

## 背景 / 症状

> アームしてモータを回した後にもう一度ディスアームしたところ、**LED がディスアームの緑点滅にならず、
> 消えたり飛行モードの色のままだったりする。LED がおかしい時はモータも回らず、
> スロットルを上げても反応しない。そこからもう少し上げると急にスラスターが急回転した。**

## ⚠ これは 2026-09-11 に一度診断され、修正されないまま残っていた問題

[`20260911_v7_arm_gate_recountdown_and_led_unhandled_states.md`](20260911_v7_arm_gate_recountdown_and_led_unhandled_states.md)
に**ほぼ同一の症状**が記録され、原因候補まで特定されている。当該記録の「対応」は
**「コード変更はまだ行っていない」**。推奨された 5 項目（`else` の追加、観測性の追加など）も未実施。

## 原因（コードから確定した事実）

### (1) ★`led_control()` に最終 `else` が無い★

`control.cpp:680-751` は `else if` の連鎖で、**どの条件にも当たらないと WS2812 に一度も書かずに抜ける**
＝ **直前の色のまま固まる**。分岐は以下だけ:

```
Arm_flag == 0 || 1
Arm_flag == 2 && Bench_mode != BENCH_OFF
Arm_flag == 2 && !g_arm_gate_ok
Arm_flag == 2 && Ftc_mode
Arm_flag == 2 && Flight_mode == NORMAL
Arm_flag == 2 && Flight_mode == MODE_HOVERING
Arm_flag == 3
          ← else が無い
```

### (2) 未処理なのは `Arm_flag == 4` **だけ**（0911 の候補 (b) は解消済み）

0911 が挙げたもう一方の候補「`Flight_mode == MODE_FTC && Ftc_mode == 0`」は**既に潰されていた**。
`Flight_mode = NORMAL;` が**無条件で**書かれ（`control.cpp:1701`）、その後 `Ftc_mode` のときだけ
`MODE_FTC` に上書きされる（`:1749`）。よって `Flight_mode == MODE_FTC ⟺ Ftc_mode == 1` が成立し、
`led_control()` の枝で必ず拾われる。

**残る未処理状態は `Arm_flag == 4`（ログ吸い出し）ただ一つ。**

### (3) `Arm_flag == 4` は症状 3 つのうち 2 つを直接説明する

`Arm_flag == 4` の枝（`control.cpp:986-`）は:

- **`motor_stop()`** → ⚠ **スロットルを上げても一切反応しない**
- `rgbled_switch(led)` を自前で叩き、`led` を 1 秒ごとに 0/1 トグル → ⚠ **LED が消えたり点いたり**
- `led_control()` 側には枝が無い → ⚠ **直前（飛行モード）の色のまま固まることもある**

**「消えたり」「飛行モードの色のまま」という両方の報告**が、この 1 状態で説明できる。

### (4) 入口は `logdata_out_com()`。ディスアーム直後は毎周期ポーリングされている

`Arm_flag == 3` かつ `LockMode == 0` のとき、`lock_com()` が 0 なら**そのまま下へ落ちて**
`logdata_out_com()` が評価される（`control.cpp:979`）。ディスアーム完了時は
`LockMode = 0, Arm_flag = 3`（`:889-890`）なので、**ディスアーム直後が常にこの状態**。

条件は `Chdata[LOG] < SW_MID` ＋ スティック 4 隅（スロットル下・ch0 下・ch3 上・ch1 上、
許容 ±80、**50 周期＝125 ms 保持**）。

⚠ **`Chdata[LOG] < SW_MID` は「LOG スイッチが OFF 側」という意味で、通常の待機姿勢そのもの。**
つまり実質的にスティック操作だけが入口を守っている。

⚠ **2026-09-16 に私がこのガードを `Chdata[4]`（当時 SERVO）から `Chdata[LOG]`（ch7）へ変えている。**
ただし**旧実装でもペイロードスイッチが下なら同様に開いていた**し、
**0911 の報告は旧実装の時点で出ている**ので、**この変更が原因ではない**。
⚠ 変わったのは「どのスイッチが守っているか」だけ。ch7 の実際の値は未確認。

### (5) 「急回転」は離陸ゲートが開く瞬間（別機構）

ディスアーム時に **`g_arm_gate_ok = 0`** が明示的に書かれる（`control.cpp:877`）。
再アーム後は `warm 1.5 s + hold 1.0 s = 2.5 s` のカウントダウンが走り、その間

- 400 Hz 側がモータを止める
- `nmpc_run` も false（`:2305`）

**この間スロットルを上げても何も起きない。** そしてゲートが開いた瞬間、
duty は `Disable_duty = 0.1` から **既に上げてあるスロットル相当の `u_hover` へ一気に飛ぶ**。

> ⚠ **「反応しないのでもう少し上げる → 急回転」は、この機構そのもの。**
> スロットルを上げた状態でゲートが開くと、意図しないフルスピンが出る。**安全上の欠陥。**

⚠ なお `sticks_neutral()` は**アーム時**にスロットル < `CH3MIN+400` を要求しており（`:1066`）、
高スロットルでのアーム自体は防がれている。防げていないのは**アーム後・ゲート開放前**の区間。

## 対応

**本記録は調査のみ。コード変更は行っていない。**

提案（優先順）:

1. ⚠ **`led_control()` に最終 `else` を足す**（例: 紫の高速点滅）。
   **「どの枝にも当たらなかった」が正常色に化けるのが最悪**で、今回まさにそれが起きた。0911 の推奨 2 と同じ
2. ⚠ **`Arm_flag == 4` に専用の枝を足す**（ログ吸い出し中と分かる色）
3. ⚠ **ゲート開放時にスロットルが低いことを要求する**（(5) の急回転を潰す）。
   例: `g_arm_gate_ok` を立てる条件に `T_ref*T_ref_coe < Flight_duty` を加える
4. `logdata_out_com()` の保持時間を 125 ms → 1 s 程度に延ばす、もしくは
   LOG スイッチを**明示的に ON 側**にすることを要求する（現状は OFF 側が入口）
5. 観測性: `Arm_flag` / `LockMode` / `g_arm_gate_ok` / `Flight_mode` をログに出す（0911 の推奨 1、未実施）

## 検証結果

- (1)(2)(3)(4)(5) はすべて**ソースから確定**（分岐の網羅、状態遷移、定数値）
- ⚠ **実機で実際にどの状態を踏んだかは確認できていない。**
  `Arm_flag` / `LockMode` / `g_arm_gate_ok` は**どのログにも出ていない**ため。
  0911 で「先に観測性を足すこと」と書かれた項目が未実施のまま同じ壁に当たっている
- ⚠ ch7（LOG）の実際の生値は未確認
