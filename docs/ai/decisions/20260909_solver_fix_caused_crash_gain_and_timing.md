# ソルバ修正で墜落。原因は「実効ゲイン 1.61 倍の未補正」と「反復 10 回の時間超過」の 2 つ

- **日付**: 2026-09-09
- **種別**: bugfix
- **対象**: `Benzen_NMPC/nmpc_params.hpp`(`R_u`, `admm_max_iter`)
- **タグ**: #Benzen_NMPC #墜落 #実効ゲイン #R_u #admm_max_iter #計算時間 #10ms予算 #回帰

## 背景 / 症状

[`20260909_solver_fix_applied.md`](20260909_solver_fix_applied.md) の修正を焼いたところ、
**離陸直後に振動して墜落した。** ユーザの見立ては「`admm_max_iter=10` で 10 ms に入っていないのでは」。

## 原因 / 判断根拠

**確認済み事実。原因は 2 つあり、どちらも修正を入れた側（＝こちら）の見落とし。**

**① 実効ループゲインが 1.61 倍になったのに補正しなかった。**

勾配の使い方のバグは写像の固有値を −1 にし、不動点を**正しい解の半分**にしていた。
つまり**バグ自体が実効ゲインを半分に落とす安定化装置として働いていた**。
これを直せばゲインが戻るのは自明だったのに、`R_u` を据え置いたまま焼いた。

同じ姿勢誤差 8.6° に対する実効 `|Δu|`（ホスト実測）:

| 設定 | 実効 \|Δu\| |
|---|---|
| 修正前 `R_u=120, iter=2` | **0.0166** |
| 修正後 `R_u=120, iter=10` ← 墜落 | **0.0268（1.61 倍）** |
| 修正後 `R_u=320, iter=4` | **0.0164（一致）** |

機体は既に安定余裕が薄い（`p` の 34.8 % が 3–6 Hz、`q` の 55.7 % が 1–3 Hz）ところへ
**ループゲインを 1.6 倍**にしたので、離陸直後に振動したのは当然だった。

**② `admm_max_iter = 10` は時間予算を超える。ユーザの見立ては正しい。**

LLT solve 1 回は 120×120 の前進後退代入 = **14,400 MAC**。
Pico2 (Cortex-M33, 150 MHz, 単精度 FPU) で 2–4 cycle/MAC とすると **190–380 µs/回**。
8 回追加で **1.5–3.1 ms**。

| | `iter_us` | `loop_us` | 判定 |
|---|---|---|---|
| 修正前 | 6.4 ms | 8.9 ms | 予算内 |
| +8 反復（楽観） | 7.9 ms | **10.4 ms** | **超過** |
| +8 反復（標準） | 8.7 ms | **11.2 ms** | **超過** |
| +8 反復（悲観） | 9.5 ms | **12.0 ms** | **超過** |

**3 通りの見積りすべてで 10 ms を超える。** 制御周期が伸びれば、余裕の薄い系はそれだけで不安定になる。

**確認済み事実。10 回は最初から過剰だった。**
`R_u` で実効ゲインを戻したうえで測り直すと、**4 回で 10 回と同じ結果**になる
（ホスト: `lag1 +0.999`、追従 0.50/0.49/0.69、飽和 0.2 %。iter=10 と数値まで一致）。
前回 iter=10 を選んだのは **`R_u=120` のまま（＝ゲイン 1.6 倍のまま）測った結果**で、
動作点がずれた状態でのチューニングだった。

## 対応

- `R_u` **120 → 320**（補間で実効ゲイン一致点は 322）
- `admm_max_iter` **10 → 4**（元の 2 回に対し +2 回 = +0.4–0.8 ms）
- 勾配修正・安全弁・`admm_rho=1.0`・`admm_lambda_max=30` は据え置き

**却下した案**: 修正ごと revert する。チャタリング（実効操作量の 7 割が無駄）は実在の問題で、
戻すと `0909_v1` の状態に戻るだけ。**ゲインと時間を合わせれば修正は有効**である。

## 検証結果

ホスト閉ループ（モータ遅れ 50 ms）:

| | 実効ゲイン | ラグ1 | 振幅比 R/P/Y | 相関 R/P/Y | 飽和 |
|---|---|---|---|---|---|
| 修正前 | 0.0166 | −0.962 | 0.42/0.48/0.53 | 0.24/0.27/0.51 | 23.4 % |
| 墜落した設定 | 0.0268 | +0.998 | 0.53/0.52/0.91 | 0.44/0.43/0.92 | 0.5 % |
| **今回** | **0.0164** | **+0.999** | 0.50/0.49/0.69 | 0.37/0.35/0.76 | **0.2 %** |

**実効ゲインは修正前と一致（差 1.2 %）、チャタリングは消えている。**
安全弁の発動も減った（±11 deg で `lambda_reset=0, nonfinite=0`）。

- ビルド成功。`text 678224 / bss 352560`（前回と同じ）。改行コード不変。
- **実機では未検証。飛ばす前に必ず `iter_us` / `loop_us` を測ること。**
- ⚠ **墜落時のログを未入手。** `iter_us`/`loop_us`/`#solver:` 行があれば
  ①と②のどちらが支配的だったかを確定できる。

## 次に触る人へ

- **バグが安定化装置になっていたら、直すのと同時にゲインを戻す。** 本件はまさにそれで、
  「1 回に 1 つだけ変える」原則に従って `R_u` を据え置いたことが裏目に出た。
  **実効ゲインを変えないための変更は、1 つの変更として数えるべきだった。**
- **チューニングは必ず正しい動作点で行う。** iter=10 を選んだ測定は
  ゲインが 1.6 倍ずれた状態で取ったもので、そこで決めた値は動作点が戻ると意味を失った。
- **反復回数のような「計算量に直結するノブ」は、演算数から実機時間を見積もってから決める。**
  ホストの実測時間をそのまま外挿してはいけない（本件では 14,400 MAC という演算数で見積もった）。
