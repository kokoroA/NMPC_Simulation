# Repository Rules — research_project（常時参照レイヤ）

> **入口ファイル。** 最小・固定で保つこと。詳細な経緯は `docs/ai/decisions/` を grep で引く。
> 手順の全文は [`skills.md`](../../skills.md)。**このファイル単体でも最低限の運用が回るよう §0 を置く。**

## 0. 作業ルーチン（全 AI ツール共通・必読）

このリポジトリは過去の設計判断・失敗・却下案を `docs/ai/decisions/` に蓄積している。
**同じ失敗を再現しないことが唯一の目的**なので、次の 2 つは必ず実行すること。

### 着手前（実装・修正に手を付ける前に必ず 1 回）

```bash
grep -ril "検索語" docs/ai/decisions/
```

タスクに含まれる固有名詞（関数名・パラメータ名・エラー文言・シナリオ名）で検索する。
検索語の例: `ADMM`, `SR2`, `TR1`, `RTI`, `Pico`, `RP2350`, `core1`, `N=`, `duty`,
`EIGEN_NO_MALLOC`, `飽和`, `発散`, `FDI`, `故障`, `sysid`

- ヒットしたら**全文を読む**。
- 過去に却下された案は、**当時から何が変わったかを示さずに再提案しない**。
- 最初の応答で、参照した decision 名（または「関連する過去記録なし」）を 1 行で示す。

### 完了後（下記に該当したら必ず記録）

バグ原因の特定 / 設計判断 / パラメータ変更 / **試して失敗した・ボツにした** / 30 分以上かかった調査。

`docs/ai/decisions/YYYYMMDD_概要.md` を作成し、[`INDEX.md`](decisions/INDEX.md) に 1 行追記する。
書くのは **「なぜ」だけ**（何を変えたかは git diff が持っている）。推測と確認済み事実は区別する。
検証していないなら「未検証」と正直に書く。

typo・フォーマット・リネームなど再現価値のない作業は記録しない。

### 何が記録されているかの目次

- **一覧: [`docs/ai/decisions/INDEX.md`](decisions/INDEX.md)**
  INDEX は目次でしかない。該当しそうな行を見つけたら**必ず本文を全部読む**こと。
  一覧だけで「知っている」と判断しないこと。

### 検証の仕組み（クローンしたら 1 回だけ設定する）

```bash
git config core.hooksPath .githooks
```

これで commit 前に [`scripts/check_memory.py`](../../scripts/check_memory.py) が走り、
**INDEX への追記漏れ・decision の必須項目欠け・リンク切れ**を機械的に弾く。
コードを触ったのに記録が無い場合は**警告だけ**出す（記録不要な変更もあるため、判断は人に残す）。
同じ検査は CI（`.github/workflows/memory-check.yml`）でも走るので、`--no-verify` では抜けられない。

> ⚠ **「AI が過去記録を読んだか」は原理的に検証できない。** 検証できるのは
> 「書いたか」「整合しているか」だけである。読ませる仕組み（`@` import / `alwaysApply` /
> フック）と、書けたかを確かめる仕組み（hook / CI）は別物として両方用意してある。

> ⚠ `Benzen_NMPC` はサブモジュール配下だが、**decision は必ず親リポジトリのここに書く**
> （記憶を 1 か所に集約しないと grep で引けなくなるため）。

## 1. プロジェクトの正体と現在のフェーズ

卒研テーマは **「NMPC を用いたヘキサコプタの耐故障制御（FTC）」**（完成目標 2026 年 9〜10 月）。
位置制御を意図的に放棄して状態を**姿勢 5 次元に縮約**し、外部カメラ・GPS を使わず
**IMU と安価な小型マイコンのみ**でフル非線形 MPC を実時間動作させる点が主張。

**現在は実機実験フェーズ。主戦場は `Benzen_NMPC`（Pico 2 W ファームウェア）。**
シミュレータは検証済みの参照実装であり、原則として実機側を追随させる方向で使う。

## 3. アーキテクチャ方針（変更時は理由を decisions に残す）

- **状態・入力**: `x = [φ, θ, p, q, r]`（NX=5）、6 モータの duty ∈ [0,1]（NU=6）。
  実機のモータ順は **`[FR, FL, MR, ML, RR, RL]`**（シミュの M1..M6 とは並びが違う。対応表は `plan.md`）。
- **実機は絶対モード**（U は絶対 duty、`U_ref` = スロットル由来のホバー baseline）。
  シミュの**加算合成（PKG-C）は C++ 未実装**。この差は既知かつ意図的なので、勝手に片方へ寄せない。
- **ソルバ**: 凝縮形 + RTI（1 反復）+ TR1（$S_u$ のランク1更新）+ SR2（Hessian のランク2更新）
  + ADMM（box 制約）。`H = S_uᵀ Q S_u + R` のフル再構築は計算量的に禁じ手。
- **コア分担**: **core1 = 100 Hz**（EKF → 参照生成 → `nmpc_step` → duty 書込）、
  **core0 = 400 Hz**（clamp・フェイルセーフ・ZOH 出力）。この分担を崩さない。
- **高度制御は NMPC に入れない**。スロットルは PID／スティックのまま。
  `B_c · 1 = 0` により共通モード（推力）と差分モード（姿勢）が分離することが根拠。
- **耐故障**は `η` を **box 制約の縮減と `U_ref` シフト**で表現する。
  故障パターンごとの分岐や専用ミキシングは書かず、ソルバに再配分を最適化させる。

## 4. 基本制約

1. **実機は単精度 float・動的確保禁止（`EIGEN_NO_MALLOC`）**。`new`/`malloc`/`std::vector` を
   制御ループに持ち込まない。行列は静的確保（主要行列 計約 200 KB / SRAM 520 KB）。
2. **`N`（予測ホライズン）は計算時間とメモリの両方に効く最重要ノブ。**
   現行値は **`nmpc_params.hpp` の `N = 17`**（`plan.md` の `N=20` は古い）。
   **`nmpc_params.hpp` が唯一の正**。変えたら必ず実測し直す。
3. **性能は「制御周期 10 ms（100 Hz）に収まるか」で評価する。**
   直近実測: ソルバ本体 **平均 8.7 ms**、**周期全体 10.6 ms** → **わずかに超過中**。
4. `Params`（Python）↔ `nmpc_params.hpp`（C++）の対応を崩さない。乖離させるなら理由を記録する。
5. **`CMakeLists.txt` の Eigen インクルードは別プロジェクトの絶対パスをハードコード**している。
   環境を移すと必ず壊れる。
6. 大容量バイナリ（`venv/`, `*.pptx`, `.DS_Store`, `build/`, `eigen/`, `pico-sdk`）はコミットしない。
7. ドキュメントは**日本語**で、既存の記法（判断に「意図」を併記する形式）に合わせる。

## 5. 現在の到達点（2026-08-20 時点）

- **実機で姿勢限定 NMPC が（ほぼ）実時間動作することを確認済み**。ソルバ本体は 100 Hz の内側。
- メモリは RP2350 の SRAM 520 KB に対し余裕あり。
- システム同定を実施済み（推力係数・モータ一次遅れ・二線振り子による慣性モーメント）→ `Benzen_NMPC/docs/`。
- シミュでは 1 発完全故障・対向 2 発故障は姿勢維持可能、
  **隣接 2 発故障はピッチ軸の権限を失うため困難**（配置依存の限界）。
- 予稿は日本航空宇宙学会向けに執筆済み（実機の計算時間実測まで反映）。

### 未解決（予稿に明記した優先順）

1. **制御周期全体を 10 ms 以内に収める最適化**（`N` 短縮または周辺処理の削減）。
2. **実機での健全飛行の安定化。**
3. **実機での 1 発故障飛行の達成。**
4. FDI 推定器は未実装。ψ は未モデル化。四元数化（特異点回避）は将来課題。
