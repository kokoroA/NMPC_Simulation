# Global Layer 昇格候補（プロジェクト非依存の教訓メモ）

> ここは**草案置き場**。他プロジェクトへ展開する価値がありそうなルール・デバッグ手法を、
> 精度を気にせず先に書き溜める場所。運用手順は [`skills.md`](../../skills.md) §3-2 を参照。
>
> - 迷ったら**書く側に倒す**（消すのは後からできる）
> - 出典として必ず `docs/ai/decisions/` の該当ファイルを添える
> - 「汎用度: 要検証」のまま放置してよい。断定できるようになったら格上げする

---

## 記憶の入口は小さく固定し、詳細は検索で取りに行く
- **主張**: 常時読み込むファイル（`CLAUDE.md` / `.cursorrules` 等）は数千文字に固定し、増える一方の経緯は別ディレクトリに追記して grep で引く。
- **理由**: 入口が肥大するとプロンプトキャッシュが毎回無効化され、コストと待ち時間が増える。入口が不変なら過去ログをいくら積んでも常時コストは一定に保てる。
- **出典**: docs/ai/decisions/000000_setup_intelligence.md
- **汎用度**: 高

## 同一内容の設定ファイルはコピーせずシンボリックリンクにする
- **主張**: `.clinerules` / `.cursorrules` / `AGENTS.md` のようにツールごとに名前が違うだけの規約ファイルは、実体を 1 つにしてリンクで生やす。
- **理由**: コピーは必ず片方だけ古くなる。「どちらが正か分からない規約」は規約が無いより悪い。構造的に不整合を起こせなくするほうがレビューより確実。
- **注意**: Windows 環境やシンボリックリンクを解決しないツールでは、生成スクリプトによる同期に切り替える必要がある。
- **出典**: docs/ai/decisions/000000_setup_intelligence.md
- **汎用度**: 中（実行環境依存）

## 失敗・却下の記録は成功の記録より価値が高い
- **主張**: 「試したが駄目だった案」と「その却下理由」を必ず残す。成功したコードは差分を読めば分かるが、通らなかった道は誰の記憶にも残らない。
- **理由**: 記録がないと、次のセッションの自分（や他人）が同じ案を再提案し、同じ時間を溶かす。却下理由まで書いてあれば、前提が変わったときだけ再検討できる。
- **出典**: docs/ai/decisions/000000_setup_intelligence.md
- **汎用度**: 高

## 検索されるために書く（エラー文言は原文のまま貼る）
- **主張**: 記録には要約ではなく、エラーメッセージ・変数名・パラメータ名を**そのままの文字列**で含める。タグも惜しまず付ける。
- **理由**: 過去ログは読まれるのではなく grep される。要約しかない記録は検索に引っかからず、存在しないのと同じ。
- **出典**: docs/ai/decisions/000000_setup_intelligence.md
- **汎用度**: 高

## 「なぜ」だけを書き、「何を変えたか」は書かない
- **主張**: 意思決定録には理由・却下案・検証結果を書き、差分の説明は書かない。
- **理由**: 何を変えたかは git log と diff が正確に保持している。人間・AI が失うのは常に意図のほうで、そこだけが手書きの価値がある。
- **出典**: docs/ai/decisions/000000_setup_intelligence.md
- **汎用度**: 高

## 数値実験を伴うプロジェクトでは起動時サニティチェックを回帰テストとして使う
- **主張**: シミュレータや数値ソルバでは、起動時に前提条件（次元・保存則・行列の性質・符号）を自動検査する関数を用意し、変更のたびに必ず通す。
- **理由**: この種のコードはユニットテストを書きにくい一方、壊れても例外を出さずに「それらしい間違った数値」を返す。前提の自動検査が事実上の回帰テストになる。
- **出典**: 本リポジトリ `program/NMPC_simulation/nmpc_simulation.py` の `sanity_checks()`（24 項目）
- **汎用度**: 中（数値計算・制御・シミュレーション系）

## 記録の仕組みより「読ませる仕組み」のほうが壊れやすい
- **主張**: 過去ログを蓄積する仕組みを作ったら、それを**強制的にコンテキストへ注入する経路**まで実装して初めて完成とみなす。ポインタ（「◯◯を読め」という指示）は強制ではない。
- **理由**: 書く側は作業の締めくくりとして自然に実行されるが、読む側はタスク開始時の「早く本題に入りたい」圧力の中にあり、自発性に任せると素通りする。読まれない記録は存在しないのと同じ。
- **手段の例**: 入口ファイルの import 展開、セッション開始フック、CI での必須チェック。
- **出典**: docs/ai/decisions/20260820_activate_memory_hooks.md
- **汎用度**: 高

## 補助的な自動化は必ず fail-open にする
- **主張**: 開発体験を良くするためのフック・スクリプトは、例外を握りつぶして常に成功終了させる。
- **理由**: 補助機能の失敗で本体（セッション起動、ビルド、コミット）が止まるのは費用対効果が逆転している。壊れたら「効かなくなる」だけで済む設計にする。
- **例外**: セキュリティチェックや破壊的操作のガードは逆に fail-closed にすべき。区別の基準は「止めなかった場合の損害が、止めた場合の損害を上回るか」。
- **出典**: docs/ai/decisions/20260820_activate_memory_hooks.md
- **汎用度**: 高

## 環境に何が入っているかを確認してからコマンドを書く
- **主張**: `jq` や特定の CLI を前提にする前に `which` で存在を確認する。無ければ確実にある手段（python3 標準ライブラリ等）へ切り替える。
- **理由**: 定番ツールほど「入っているはず」と思い込みやすい。フックや CI のように**エラーが見えにくい場所**でこれをやると、静かに動かないものが出来上がる。
- **出典**: docs/ai/decisions/20260820_activate_memory_hooks.md
- **汎用度**: 高

## リポジトリ調査を git の視界だけで済ませない
- **主張**: `git ls-files` / `git status` でプロジェクト構造を把握したら、必ず `find` / `ls` で実ファイルも確認する。両者が食い違う場所こそ重要物が置かれていることがある。
- **理由**: サブモジュール配下・未追跡ディレクトリ・sparse な worktree の中身は git のリストに現れない。git だけを見た調査は「無い」と静かに誤答し、その誤りが下流の判断すべてを汚染する。
- **兆候**: `git check-ignore` が `fatal: Pathspec ... is in submodule` を返す、ディレクトリが存在するのに追跡ファイルが 0 件、README が参照するパスが git のリストに無い。
- **出典**: docs/ai/decisions/20260820_hardware_phase_correction.md
- **汎用度**: 高

## 「唯一の正」をファイル単位で宣言しておく
- **主張**: 同じパラメータが計画書・レポート・ヘッダ・論文の 4 か所に書かれるなら、どれが正かをルールとして明記する（例: 「`nmpc_params.hpp` が唯一の正、計画書の値は古い」）。
- **理由**: ドキュメントは実装より必ず遅れる。どれが正かが決まっていないと、読み手ごとに違う値を信じて作業し、原因の分かりにくい不整合を生む。
- **出典**: docs/ai/decisions/20260820_hardware_phase_correction.md
- **汎用度**: 高

## 意図的な差異は「意図的である」と書いておく
- **主張**: 参照実装と本番実装で仕様が違う場合、差異の内容だけでなく **「これは既知かつ意図的であり、勝手に揃えてはいけない」** と明示する。
- **理由**: 差異だけが記録されていると、次に読んだ人（や AI）が「バグ」「移植漏れ」と解釈して善意で片方に寄せてしまう。何もしないことを選ぶには、何もしない理由が要る。
- **出典**: docs/ai/decisions/20260820_hardware_phase_correction.md
- **汎用度**: 高

## 共有ドキュメントは「どの経路で誰に届くか」まで設計する
- **主張**: 手順と知識をファイル分割したら、**分割の境界が配布経路の境界と一致していないか**を必ず確認する。片方しか届かない読み手が生まれていないか、実際に読み手側の視点でファイルを開いて検証する。
- **理由**: 関心事による分離（手順／知識）は正しい設計だが、ツールごとに読み込む入口ファイルは違う。手順を全部「片方のツールしか読まないファイル」へ寄せると、他のツールにとっては手順が消滅する。分離した瞬間は誰も気づかない。
- **検証法**: 各読み手の入口ファイルを実際に `head` して、必要な情報が本当に見えるか確かめる。「書いたはず」を根拠にしない。
- **出典**: docs/ai/decisions/20260822_multi_tool_entrypoints.md
- **汎用度**: 高

## 同じ内容を複数箇所に置くならシンボリックリンクにする
- **主張**: 複数ツールが別々のファイル名で同じ設定を要求する場合、実体を 1 つに決めて残りは symlink にする。コピーは最後の手段。
- **理由**: コピーは必ず片方だけ古くなる。しかも「両方存在して内容が違う」状態は、どちらが正か読み手に判断できず、静かに誤った方が信じられる。
- **例外**: frontmatter など**ファイル固有のメタデータが必須**な形式は symlink にできない。その場合も本文にルールを複製せず、実体への参照＋要約に留めて二重管理の面積を最小化する。
- **出典**: docs/ai/decisions/20260822_multi_tool_entrypoints.md
- **汎用度**: 高

## 自分で書いた要件は、書いた直後に満たしているか確認する
- **主張**: ドキュメントに「〜を保つこと」と制約を書いたら、その場で実物を検査して既に満たしているかを確かめる。
- **理由**: 要件を書く行為は「決めた」だけで「やった」ではないのに、書いた本人は完了したと記憶しやすい。とくに自分宛ての運用ルールは、レビューする第三者がいないので誰にも検出されない。
- **出典**: docs/ai/decisions/20260822_multi_tool_entrypoints.md
- **汎用度**: 高
