# Global Layer 昇格候補（プロジェクト非依存の教訓メモ）

> ここは**草案置き場**。他プロジェクトへ展開する価値がありそうなルール・デバッグ手法を、
> 精度を気にせず先に書き溜める場所。運用手順は [`skills.md`](../../skills.md) §3-2 を参照。
>
> - 迷ったら**書く側に倒す**（消すのは後からできる）
> - 出典として必ず `docs/ai/decisions/` の該当ファイルを添える
> - 「汎用度: 要検証」のまま放置してよい。断定できるようになったら格上げする

## 記憶の入口は小さく固定し、詳細は検索で取りに行く
- **主張**: 常時読み込むファイル（`CLAUDE.md` / `.cursorrules` 等）は数千文字に固定し、増える一方の経緯は別ディレクトリに追記して grep で引く。
- **理由**: 入口が肥大するとプロンプトキャッシュが毎回無効化され、コストと待ち時間が増える。入口が不変なら過去ログをいくら積んでも常時コストは一定に保てる。
- **出典**: docs/ai/decisions/000000_setup_intelligence.md
- **汎用度**: 高

## 同一内容の設定ファイルはコピーせずシンボリックリンクにする
- **主張**: `.clinerules` / `.cursorrules` / `AGENTS.md` のようにツールごとに名前が違うだけの規約ファイルは、実体を 1 つにしてリンクで生やす。
- **理由**: コピーは必ず片方だけ古くなる。「どちらが正か分からない規約」は規約が無いより悪い。構造的に不整合を起こせなくするほうがレビューより確実。
- **注意**: Windows 環境やシンボリックリンクを解決しないツールでは、生成スクリプトによる同期に切り替える必要がある。
- **出典**: docs/ai/decisions/000000_setup_intelligence.md
- **汎用度**: 中（実行環境依存）

## 失敗・却下の記録は成功の記録より価値が高い
- **主張**: 「試したが駄目だった案」と「その却下理由」を必ず残す。成功したコードは差分を読めば分かるが、通らなかった道は誰の記憶にも残らない。
- **理由**: 記録がないと、次のセッションの自分（や他人）が同じ案を再提案し、同じ時間を溶かす。却下理由まで書いてあれば、前提が変わったときだけ再検討できる。
- **出典**: docs/ai/decisions/000000_setup_intelligence.md
- **汎用度**: 高

## 検索されるために書く（エラー文言は原文のまま貼る）
- **主張**: 記録には要約ではなく、エラーメッセージ・変数名・パラメータ名を**そのままの文字列**で含める。タグも惜しまず付ける。
- **理由**: 過去ログは読まれるのではなく grep される。要約しかない記録は検索に引っかからず、存在しないのと同じ。
- **出典**: docs/ai/decisions/000000_setup_intelligence.md
- **汎用度**: 高

## 「なぜ」だけを書き、「何を変えたか」は書かない
- **主張**: 意思決定録には理由・却下案・検証結果を書き、差分の説明は書かない。
- **理由**: 何を変えたかは git log と diff が正確に保持している。人間・AI が失うのは常に意図のほうで、そこだけが手書きの価値がある。
- **出典**: docs/ai/decisions/000000_setup_intelligence.md
- **汎用度**: 高

## 数値実験を伴うプロジェクトでは起動時サニティチェックを回帰テストとして使う
- **主張**: シミュレータや数値ソルバでは、起動時に前提条件（次元・保存則・行列の性質・符号）を自動検査する関数を用意し、変更のたびに必ず通す。
- **理由**: この種のコードはユニットテストを書きにくい一方、壊れても例外を出さずに「それらしい間違った数値」を返す。前提の自動検査が事実上の回帰テストになる。
- **出典**: 本リポジトリ `program/NMPC_simulation/nmpc_simulation.py` の `sanity_checks()`（24 項目）
- **汎用度**: 中（数値計算・制御・シミュレーション系）

## 記録の仕組みより「読ませる仕組み」のほうが壊れやすい
- **主張**: 過去ログを蓄積する仕組みを作ったら、それを**強制的にコンテキストへ注入する経路**まで実装して初めて完成とみなす。ポインタ（「◯◯を読め」という指示）は強制ではない。
- **理由**: 書く側は作業の締めくくりとして自然に実行されるが、読む側はタスク開始時の「早く本題に入りたい」圧力の中にあり、自発性に任せると素通りする。読まれない記録は存在しないのと同じ。
- **手段の例**: 入口ファイルの import 展開、セッション開始フック、CI での必須チェック。
- **出典**: docs/ai/decisions/20260820_activate_memory_hooks.md
- **汎用度**: 高

## 補助的な自動化は必ず fail-open にする
- **主張**: 開発体験を良くするためのフック・スクリプトは、例外を握りつぶして常に成功終了させる。
- **理由**: 補助機能の失敗で本体（セッション起動、ビルド、コミット）が止まるのは費用対効果が逆転している。壊れたら「効かなくなる」だけで済む設計にする。
- **例外**: セキュリティチェックや破壊的操作のガードは逆に fail-closed にすべき。区別の基準は「止めなかった場合の損害が、止めた場合の損害を上回るか」。
- **出典**: docs/ai/decisions/20260820_activate_memory_hooks.md
- **汎用度**: 高

## 環境に何が入っているかを確認してからコマンドを書く
- **主張**: `jq` や特定の CLI を前提にする前に `which` で存在を確認する。無ければ確実にある手段（python3 標準ライブラリ等）へ切り替える。
- **理由**: 定番ツールほど「入っているはず」と思い込みやすい。フックや CI のように**エラーが見えにくい場所**でこれをやると、静かに動かないものが出来上がる。
- **出典**: docs/ai/decisions/20260820_activate_memory_hooks.md
- **汎用度**: 高

## リポジトリ調査を git の視界だけで済ませない
- **主張**: `git ls-files` / `git status` でプロジェクト構造を把握したら、必ず `find` / `ls` で実ファイルも確認する。両者が食い違う場所こそ重要物が置かれていることがある。
- **理由**: サブモジュール配下・未追跡ディレクトリ・sparse な worktree の中身は git のリストに現れない。git だけを見た調査は「無い」と静かに誤答し、その誤りが下流の判断すべてを汚染する。
- **兆候**: `git check-ignore` が `fatal: Pathspec ... is in submodule` を返す、ディレクトリが存在するのに追跡ファイルが 0 件、README が参照するパスが git のリストに無い。
- **出典**: docs/ai/decisions/20260820_hardware_phase_correction.md
- **汎用度**: 高

## 「唯一の正」をファイル単位で宣言しておく
- **主張**: 同じパラメータが計画書・レポート・ヘッダ・論文の 4 か所に書かれるなら、どれが正かをルールとして明記する（例: 「`nmpc_params.hpp` が唯一の正、計画書の値は古い」）。
- **理由**: ドキュメントは実装より必ず遅れる。どれが正かが決まっていないと、読み手ごとに違う値を信じて作業し、原因の分かりにくい不整合を生む。
- **出典**: docs/ai/decisions/20260820_hardware_phase_correction.md
- **汎用度**: 高

## 意図的な差異は「意図的である」と書いておく
- **主張**: 参照実装と本番実装で仕様が違う場合、差異の内容だけでなく **「これは既知かつ意図的であり、勝手に揃えてはいけない」** と明示する。
- **理由**: 差異だけが記録されていると、次に読んだ人（や AI）が「バグ」「移植漏れ」と解釈して善意で片方に寄せてしまう。何もしないことを選ぶには、何もしない理由が要る。
- **出典**: docs/ai/decisions/20260820_hardware_phase_correction.md
- **汎用度**: 高

## 共有ドキュメントは「どの経路で誰に届くか」まで設計する
- **主張**: 手順と知識をファイル分割したら、**分割の境界が配布経路の境界と一致していないか**を必ず確認する。片方しか届かない読み手が生まれていないか、実際に読み手側の視点でファイルを開いて検証する。
- **理由**: 関心事による分離（手順／知識）は正しい設計だが、ツールごとに読み込む入口ファイルは違う。手順を全部「片方のツールしか読まないファイル」へ寄せると、他のツールにとっては手順が消滅する。分離した瞬間は誰も気づかない。
- **検証法**: 各読み手の入口ファイルを実際に `head` して、必要な情報が本当に見えるか確かめる。「書いたはず」を根拠にしない。
- **出典**: docs/ai/decisions/20260822_multi_tool_entrypoints.md
- **汎用度**: 高

## 同じ内容を複数箇所に置くならシンボリックリンクにする
- **主張**: 複数ツールが別々のファイル名で同じ設定を要求する場合、実体を 1 つに決めて残りは symlink にする。コピーは最後の手段。
- **理由**: コピーは必ず片方だけ古くなる。しかも「両方存在して内容が違う」状態は、どちらが正か読み手に判断できず、静かに誤った方が信じられる。
- **例外**: frontmatter など**ファイル固有のメタデータが必須**な形式は symlink にできない。その場合も本文にルールを複製せず、実体への参照＋要約に留めて二重管理の面積を最小化する。
- **出典**: docs/ai/decisions/20260822_multi_tool_entrypoints.md
- **汎用度**: 高

## 自分で書いた要件は、書いた直後に満たしているか確認する
- **主張**: ドキュメントに「〜を保つこと」と制約を書いたら、その場で実物を検査して既に満たしているかを確かめる。
- **理由**: 要件を書く行為は「決めた」だけで「やった」ではないのに、書いた本人は完了したと記憶しやすい。とくに自分宛ての運用ルールは、レビューする第三者がいないので誰にも検出されない。
- **出典**: docs/ai/decisions/20260822_multi_tool_entrypoints.md
- **汎用度**: 高

## `-DX=0` を `#ifdef X` で受けてはならない
- **主張**: ビルドシステムから `-DX=0` を渡す設計にしたら、受け側は必ず `#if X` にする。`#ifdef X` は「定義の有無」しか見ないので `0` でも真になる。
- **理由**: `X=0`（無効化したつもり）と `#ifdef`（定義されていれば有効）の組み合わせは**コンパイルも警告も通る**ため、実行時に初めて症状が出る。しかも「無効にしたはずの分岐」が有効になるので、症状は元コードのどこを読んでも説明できない形で現れる。同一ファイル内に `#if` 版と `#ifdef` 版が混在しているとレビューでも見落とす。
- **見つけ方**: `-D<NAME>=` を渡している全マクロについて `grep -n "ifdef <NAME>\|defined(<NAME>)"` を掛ける。ヒットしたら全部バグ。
- **裏取りの手口**: 分岐先の定数がコンパイル時に畳み込まれるなら、その値のバイト列を成果物バイナリから直接探せば「どちらの分岐が入ったか」をソースを読まずに確定できる（例: `0.2f * 7.4` は double `1.4800000220537186`）。ソース・ビルド設定・実機挙動の三者が食い違うときに強い。
- **出典**: docs/ai/decisions/20260828_nmpc_bench_define_throttle.md
- **汎用度**: 高

## 「同じ症状が別プログラムでも出るか」で原因層を切り分ける
- **主張**: 症状が A では出て B では出ないなら原因は A/B の差分にある。両方で出るならそれは下位層（ハード・ドライバ・設定）にある。**先にこの二分をしてから原因を探す。**
- **理由**: 現象を 1 つの原因で説明しようとすると、実際には独立した 2 つの問題が絡んでいるときに必ず迷走する。切り分けが済んでいれば、片方の調査結果がもう片方の仮説を汚染しない。
- **出典**: docs/ai/decisions/20260828_nmpc_bench_define_throttle.md
- **汎用度**: 高

## 解除条件は、その条件が成立する場所から到達できるかまで確認する
- **主張**: 「A のときは状態をクリアする」という処理を、**A が偽のときにしか実行されない場所**に書いてはならない。状態のクリアは分岐の**前**で 1 回だけ行う。
- **理由**: `if (mode == X) { ... check(); }` の `check()` の中に `if (mode != X) clear();` と書いても、その行には永久に制御が到達しない。**コンパイルも警告も通り、grep すると「実装済み」に見える**ため、レビューでも見落とす。症状は「一度立ったフラグが二度と落ちない」という形で、クリア処理を読んでも説明できない形で現れる。分岐の枝ごとにクリアを書く方式も、枝が増えるたびに書き漏らすので同じ罠に落ちる。
- **見つけ方**: フラグをクリアしている行から呼び出し元を遡り、**その行に到達する条件とクリアの条件が両立するか**を確かめる。ラッチするフラグ（一度立つと自動で落ちない類）は全部これを確認する。
- **出典**: docs/ai/decisions/20260904_failsafe_rx_split_and_latch_fix.md
- **汎用度**: 高

## 保護機構は「誤検知したときに何が起きるか」まで含めて設計する
- **主張**: 異常検知のしきい値を決めるとき、**検知が正しかった場合の利得**だけでなく**誤検知したときの損害**を並べて比較する。誤検知の損害が異常そのものより大きいなら、そのしきい値は保護になっていない。
- **理由**: 「異常なら止める」は一見安全側に見えるが、止めること自体が致命的な状況（飛行中・処理中・トランザクション中）では、誤検知 1 回で確実に最悪の結果になる。とくに**下位層が日常的に立てるフラグ**（1 回のパケットロス、1 回のリトライ、瞬間的なタイムアウト）を「異常」として即断すると、正常系のノイズで保護機構が暴発する。単発ではなく**連続回数・継続時間**で判定し、既存の別条件（タイムアウト等）と役割が重複していないかを確認する。
- **付随**: 異常の原因コードは**物理現象ごとに分ける**。複数の原因に同じコードを割り当てると、ログを見ても何が起きたか判別できず、事後の原因特定が丸ごと不可能になる。
- **出典**: docs/ai/decisions/20260904_v11_failsafe_rx_framelost.md, docs/ai/decisions/20260904_failsafe_rx_split_and_latch_fix.md
- **汎用度**: 高

## 制御・信号の評価は必ず「制御周期と同じレート」のログで行う
- **主張**: 制御則の出力を、制御周期より粗いレートで記録したログで評価してはならない。**ナイキスト以上の成分は折り返して、まったく別の量に化けて見える。**
- **理由**: 100 Hz で動く制御器の出力を 10 Hz で記録すると、制御器が毎周期反転していても、ログ上では「大きくばらついている」「よく飽和している」ようにしか見えない。そこから「舵が足りない」「飽和しているので重みを下げるべきだ」という**正反対の結論**が出る。実際にはアクチュエータには余裕があり、出力の大半は無意味な高周波だった。
- **見分け方**: 出力のラグ 1 自己相関を見る。まともな制御なら +0.9 以上。**0 付近や負なら、その信号は制御ではなく数値的な振動**であり、記録レートに関わらず疑うべき。
- **付随**: 同じログの「滑らかであるはずの量」（積分された状態量など）が滑らかかどうかを確認すると、記録系の破損と現象の切り分けができる。
- **出典**: docs/ai/decisions/20260904_duty_chatter_50hz_nullspace.md
- **汎用度**: 高

## 冗長な入力を持つ系では「出力の何割が実際に効いているか」を分解して測る
- **主張**: 入力の数が制御したい自由度より多い系（冗長系）では、出力ノルムの大きさは働きの大きさを意味しない。**入力を「効く部分空間」と「ヌル空間」に分解し、それぞれの取り分を測る。**
- **理由**: ヌル空間成分はエネルギーを消費し、飽和限界を食い潰し、統計上は「よく働いている」ように見えるが、系には一切効かない。分解せずに rms や飽和率だけを見ると、実際には余裕が有り余っているのに「限界まで使っている」と誤診する。
- **やり方**: 入力→出力の写像行列の行空間へ射影し、残差をヌル空間成分とする。さらに行空間側も物理的に意味のある基底（今回なら共通モード・各軸モーメント）へ分解すると、どの自由度が食われているかまで分かる。
- **出典**: docs/ai/decisions/20260904_duty_chatter_50hz_nullspace.md, docs/ai/decisions/20260904_yaw_starves_roll_pitch.md
- **汎用度**: 中

## 設計案の可否が未同定パラメータで反転するなら、可否判定ではなくそのパラメータの測定を先にやる
- **主張**: 設計案を評価したとき、結論が「まだ測っていない値」の 1 桁で反転するなら、その時点で**評価は終わっていない**。可否を議論し続けるのではなく、**そのパラメータの測定こそが唯一の律速**であると宣言して、測定を先に片付ける。
- **理由**: 未同定パラメータの公称値（誰かが置いた仮の数字）で解いた結果は、その仮の数字の性質を調べているだけで、実物の性質を何も語らない。しかも仮の値は往々にして「もっともらしい中央値」なので、片側に倒れた結論が出ると、それが実物の性質だと錯覚しやすい。**感度掃引を必ず添え、結論が反転する境目が公称値からどれだけ離れているかを数値で示す**と、この錯覚が起きない。境目が公称値のすぐ隣にあるなら、それは「案が有望／絶望」ではなく「まだ何も分かっていない」という結論である。
- **付随**: 実装してから確かめようとしないこと。パラメータが決まっていなければ、実装が成功しても失敗しても、その原因を切り分けられない。
- **出典**: docs/ai/decisions/20260905_relaxed_hover_eval_cr_decides.md
- **汎用度**: 高

## 条件が改善する予定でも、その改善が既に前提に織り込まれていないかを先に確認する
- **主張**: 「次はハードが良くなるから通るはず」と考えたら、**過去の否定的な評価がどの数値を仮定していたかを読み直す**。改善後の値が既に使われていることがある。
- **理由**: 否定的な結論は「悲観的な仮定で出したもの」と記憶されやすいが、実際には楽観的な仮定で出していることがある。前提を確認しないまま「条件が良くなった」を理由に同じ試験を繰り返すと、同じ失敗を、より高いコストで再現する。
- **見つけ方**: 却下記録の中の具体的な数値（上限値・容量・スループット）を、これから使う実物の実測値と 1 対 1 で突き合わせる。名前ではなく数値で照合する。
- **出典**: docs/ai/decisions/20260905_relaxed_hover_eval_cr_decides.md
- **汎用度**: 高

## 点推定が取れなくても、恒等式の絶対値を取れば上界は取れる
- **主張**: 回帰で係数が同定できなかったとき、「何も分からない」と結論する前に、**モデルの恒等式を不等式に落とせないか**を試す。右辺の項が全部測定できているなら、絶対値を取るだけで係数の上界（または下界）が出る。
- **理由**: 同定は「値を 1 点に決める」問題だが、意思決定に必要なのはたいてい「ある閾値の上か下か」だけである。上界だけで判断が付くなら、識別性の議論をせずに前へ進める。しかも上界は**残差の分離ができていなくても成り立つ**ので、回帰が失敗する状況（共線性、励起不足、ノイズ）でも生き残る。
- **付随**: 公称値（誰かが置いた仮の数字）は、**「その値が正しいとすると観測されたはずのこと」を計算して検算する**と、桁違いの誤りが 1 本のログで落とせる。「その値だと到達できないはずの状態に実際に到達している」は、それだけで反証になる。
- **出典**: docs/ai/decisions/20260905_cr_upper_bound_and_yaw_hang_test.md
- **汎用度**: 高

## 実験は「知りたい量」ではなく「モデルが実際に使っている組み合わせ」を測る
- **主張**: 個々の物理量を別々に測ろうとする前に、**実装が実際に使っている形**を見る。多くの場合それは比や積であり、その組み合わせをまとめて測るほうが速く、途中の量の不確かさを迂回できる。
- **理由**: 実装が `A/B` の形でしか使っていないなら、`A` と `B` を別々に測るのは仕事が 2 倍になるうえ、両方の誤差が入る。組み合わせを直接測れば 1 回で済み、しかも「まだ誰も測っていない `B`」の不確かさが結果に伝播しない。分解が必要になるのは、別のモデルがその量を単独で要求するときだけで、それは後回しにできることが多い。
- **やり方**: 実装コードの該当行をそのまま読み、係数がどう束ねられているかを確認してから実験を設計する。
- **出典**: docs/ai/decisions/20260905_cr_upper_bound_and_yaw_hang_test.md
- **汎用度**: 高

## 平衡点近傍の挙動を直したいなら、そこで消える項を触っても無駄
- **主張**: `C·x|x|` や `C·x²` のような**原点で微分が消える項**は、平衡点近傍の線形化に現れない。平衡点付近で起きている症状（じわじわ流れる、戻らない、オフセットが残る）に対して、この種の係数をいくら動かしても効果はゼロである。
- **理由**: 制御則が使うのは値そのものではなく**感度（偏微分）**であることが多い。二乗項の感度は原点で 0 なので、係数を何桁動かしても平衡点近傍の応答は変わらない。それでも「大きくすれば効くはず」と直感で触ってしまうのは、値の大きさと感度の大きさを混同しているため。
- **見分け方**: 症状が出ている動作点で**ヤコビアンの該当要素を数値で評価する**。ゼロに近ければそのノブは無関係。効くノブは別（重み、線形項、外乱補償）にある。
- **付随**: 同じ症状でも原因が「定常外乱」か「モデル定数の誤り」かで効くノブが変わる。前者は重みか物理側の是正、後者はその定数を測って合わせる。**測れる定数はチューニングノブではない。**
- **出典**: docs/ai/decisions/20260909_cr_is_not_a_drift_knob.md
- **汎用度**: 高

## 「勾配」と「増分」を混ぜると、固有値 −1 の振動が静かに居座る
- **主張**: 反復解法で、ある点における**完全な勾配** `∇J(x_lin)` を計算しておきながら、その解を **`x_lin` からの増分ではなく絶対解として**使ってはならない。二次形式では `∇J(x_lin) = H·x_lin + c` なので、`x_new = -H⁻¹∇J(x_lin)` は `x_new = -x_lin - H⁻¹c` となり、**写像の固有値がちょうど −1** になる。
- **理由**: この振動は**減衰も発散もしない**ので、数値エラーも警告も出ず、ソルバは毎回「解けた」と報告する。しかも不動点は正解のちょうど半分なので、症状は「なんとなく効きが弱い」「出力がガタつく」という曖昧な形でしか現れない。原因を制御対象側（プラント、センサ、機構）に探しに行くと永遠に見つからない。
- **見つけ方**: **出力のラグ1自己相関**を見る。−1 に近ければ周期 2 振動であり、正常な制御ではありえない。加えて、**プラントを内部モデルと完全に同一にして閉ループを回す**。それでも症状が残れば、原因は解法の中にしかない。
- **付随**: 増分形にするか絶対形にするかは、どちらでもよいが**一貫させる**。増分形なら `x = x_lin + Δx`、絶対形なら勾配ではなく定数項 `c = ∇J(x_lin) - H·x_lin` を使う。

- **汎用度**: 高

## バグが安定化装置として働いていることがある。直すときは一度に一つにしない
- **主張**: 長く動いていた系のバグを直すとき、**そのバグが別の問題を隠している／抑えている**可能性を先に確かめる。実効ゲインを下げるバグは、モデル化されていない遅れに対する安定余裕をタダで生んでいることがある。
- **理由**: 「正しく直したのに前より悪くなる」は、直した結果ループゲインが設計値に戻り、**設計時に見落としていた遅れや飽和が初めて顔を出す**ために起きる。バグと一緒に、それが押さえ込んでいた第二のバグも同時に解放される。
- **やり方**: 修正を入れる前に、**修正後の系を机上（ホスト／シミュレータ）で回して発散しないかを確かめる**。発散するなら、修正と同時に入れるべき手当（ゲインを戻す、上限を設ける、安全弁を足す）を洗い出してから実機に持っていく。**修正を「1 つずつ入れる」原則が、この場合だけは逆に危険**になる。

## 「編集する場所」と「成果物が作られる場所」を分けたら、戻す工程まで 1 作業にする
- **主張**: ビルド設定の都合でソース一式を作業用ディレクトリへコピーしたら、**掃引で得た最終値を本体へ書き戻すところまでを不可分の 1 ステップ**として扱う。コピー先で「実装した・検証した」と言った瞬間から、本体は嘘の状態になっている。

- **見つけ方**: 完了報告の前に、**本体ツリーでビルドし直す**。ビルド済み成果物が残っていても再利用しない。今回は本体が参照先メンバ欠落で**コンパイルすら通らない**状態だったのに、成果物が既にあったせいで「ビルド済み」と報告してしまった。加えて、**成果物の逆アセンブルから定数リテラルを検索**（例: `320.0f` = `0x43a00000`）すると、ソースと成果物の乖離を一発で判定できる。
- **付随**: mtime の前後関係は強い証拠になる。**成果物より新しいソース**は「ビルド後に誰かが書き戻した」ことを意味する。

## 近似で作った行列を、別の量を逆算する式の一方の辺に使ってはいけない
- **主張**: 準ニュートン法（BFGS / SR1 / SR2 など）で更新している近似ヘシアン `H̃` は、**探索方向を作るためだけ**に使う。`b = H̃·x − g` のように、`H̃` を含む恒等式から別の量を逆算してはならない。
- **理由**: 恒等式 `g = H·x + c` が成り立つのは `H` が厳密なときだけ。近似を代入すると逆算の結果に `(H̃ − H)·x` が乗る。**誤差が `x` の大きさに比例して増幅される**うえ、`x` 自身がその逆算結果から決まるなら正のフィードバックになり、静かに発散する。
- **見つけ方**: 逆算した量を、**定義から直接組み立てた値と突き合わせる**。相対誤差を毎反復記録し、`x` のノルムと一緒にプロットする。誤差が `x` に比例して伸びていれば当たり。**近似を厳密版に差し替えて誤差が消えるか**を見るのが確定打（例: 毎周期フル再構築に切り替える）。
- **付随**: 逆算をやめて定義どおり作る方が、たいてい**計算量も減る**。逆算のために用意していた中間量（この例では勾配そのもの）が丸ごと不要になることがある。
- **出典**: docs/ai/decisions/20260909_admm_const_term_backsolve_divergence.md
- **汎用度**: 高

## ノイズを入れない机上試験は、確率的な発散を必ず見逃す
- **主張**: 制御則の机上検証では、**測定ノイズを入れた試行を複数シードで回す**。ノイズなし 1 本の「安定」は何も保証しない。
- **理由**: 正のフィードバックを持つ不安定モードは、励起されるまで顔を出さない。ノイズなしだと状態が理想軌道に貼り付いたままなので、発散の種が撒かれない。実機ではセンサノイズが常時それを撒いている。
- **実例**: ジャイロノイズ 0（rms 0.57 deg/s 相当を 0 に）では 8 シード全部が安定。ノイズを入れると**同じコードが 3/8 で発散**した。実機は「6.5 秒正常に飛んでから 90 ms で破綻」という、まさにこの確率的な出方をした。
- **やり方**: 「壊れないこと」ではなく「**何割のシードで壊れるか**」を指標にする。0/8 と 3/8 は、1 本ずつ見ていると両方「動いた／たまたま失敗した」に見えてしまう。

- **汎用度**: 高

## バグを潰すたびに「新しい不具合」が出るなら、それは順番に露出しているだけかもしれない
- **主張**: 修正のたびに別の症状で壊れる系では、**過去ログを同じ指標で測り直して、その症状が本当に新しいのかを確かめる**。古い症状が新しい顔で出ているだけのことがある。
- **理由**: 致命的な不具合が複数積み重なっている系では、**一番早く効くものだけが観測される**。それを潰すと次が見える。各修正は正しいのに、体感は「直すたびに悪くなる」になり、正しい修正を疑って巻き戻す方向へ引っ張られる。
- **やり方**: 修正の前後で**同じ健全性指標を全部並べる**（今回なら周期時間・安全弁の発動回数・出力の自己相関）。指標が軒並み改善しているのに壊れるなら、原因は別の層にある。加えて**修正前のログにその症状が既にあるか**を探す。あれば、それは新規ではなく順番待ちだった不具合である。
- **付随**: 症状が「以前から存在していた」ことが分かると、優先度も変わる。直近の変更を疑うのをやめて、**一番古い未解決の記録**に戻る。

- **汎用度**: 高

## ゲインを 1 つの入力波形で測ると、符号を取り違える
- **主張**: フィードバックゲインを変えたら、**性質の違う入力を最低 2 種類**あてて確かめる。少なくとも「正弦掃引（各項が連動する）」と「片方の項だけが立つ静的入力」の両方。
- **理由**: 状態フィードバックの各項（角度・角速度など）は、正弦入力では位相関係が固定されて必ず一緒に動く。そのため片方の重みを変えても合成ゲインが打ち消し合って「ほぼ不変」に見えることがある。ところが実機には**片方の項だけが立つ状況**（センサのドリフトで角度誤差だけが出る、目標値がステップする等）があり、そこでは打ち消しが効かず、意図と逆にゲインが増える。
- **実例**: 角速度重みを 20 → 1 に下げた。正弦掃引では低周波ゲイン 1.23 → 1.08（ほぼ不変）で発振帯だけ半減、と読めた。しかし「角度誤差あり・角速度ゼロ」では指令が **1.93 倍**に増えていた。実機はまさにその状況に当たり、離陸できなかった。
- **やり方**: ステップ応答・静的オフセット・正弦掃引を並べる。**どれか 1 つで「ゲインが下がった」と言わない。**
- **出典**: docs/ai/decisions/20260910_qp_reduction_was_a_gain_increase.md
- **汎用度**: 高

## 制御を論じる前に、推定値がセンサと整合しているかを確かめる
- **主張**: 姿勢・速度などの推定量を使う制御ログを解析するときは、**まず推定値の変化が生センサの積分で説明できるか**を検算する。説明できないログで制御ゲインを議論しても結論は出ない。
- **理由**: 推定器（EKF・相補フィルタ）はバイアス状態を持ち、それが発散すると**出力だけが滑らかにランプし、生センサは正常なまま**という形で壊れる。滑らかなので異常に見えず、制御側は「正しく」大きな修正を出すため、症状はゲイン過大や外乱に見える。
- **やり方**: `(推定値の差分) − Σ(生センサ)·dt` を区間で取り、正常時の分布と比べる。桁が違えばその区間の制御データは使えない。推定器の内部バイアス状態は**必ずテレメトリに出す**（見えないものは切り分けられない）。
- **付随**: 健全性ガードを「絶対値が範囲内か」だけで書かない。**推定値と生センサの整合**を見るガードの方が、この壊れ方を直接捕まえる。
- **出典**: docs/ai/decisions/20260910_qp_reduction_was_a_gain_increase.md
- **汎用度**: 高

## ゲインを合わせるなら「出力の大きさ」ではなく「入力と相関している成分」を合わせる
- **主張**: 制御則を作り替えたあとに旧版とゲインを揃えるときは、出力の振幅（RMS や平均絶対値）で合わせてはいけない。**入力（誤差）と相関している成分だけ**を取り出して合わせる。
- **理由**: 旧版の出力に、誤差と無相関な成分（チャタリング、ディザ、数値ノイズ、飽和による切り替わり）が混ざっていることがある。プラントがそれを低域通過で捨てているなら、その成分は**振幅には寄与するがループゲインには寄与しない**。振幅で合わせると、無相関成分の割合だけ実効ゲインを過大にしてしまう。
- **実例**: 旧版の指令は 7-8 割が姿勢に効かない 50 Hz 成分だった（指令トルクの状態説明率 R² が 0.14-0.31）。新版で同じ振幅に合わせたところ、実効ループゲインが 1.7-2.7 倍になり、機体が発振して墜落した。誤差 1 度あたりの相関成分で合わせ直すと、必要な重みは 2.5 倍だった。
- **やり方**: 旧版のログで、出力を状態（および目標値）へ回帰し、**R² と回帰係数**を出す。合わせるのは回帰係数。R² が低ければ低いほど、振幅ベースの一致は危険だという警告になる。
- **出典**: docs/ai/decisions/20260910_dither_was_masking_the_real_loop_gain.md
- **汎用度**: 高

## 「異常を検知したら再計算」は、再計算が高価なら異常より害になる
- **主張**: 差分更新（準ニュートン、ランク 1 更新、増分線形化）の健全性チェックに引っかかったとき、**その場で高価なフル再計算を同期実行してはいけない**。まず「その更新を捨てて前の整合した状態を使い続ける」を選び、フル再計算は回数と間隔を上限で縛る。
- **理由**: 健全性チェックの閾値は分布の裾に刺さりやすく、動作点が変わる（今回はゲイン重みを上げただけ）と発火率が数倍に跳ねる。フル再計算が制御周期の数倍かかる系では、それが「制御の凍結」として現れ、**検知しようとした異常（線形化が少し古い）より桁違いに大きい害**になる。しかも凍結中に状態が進むので次も発火し、嵐になる。
- **実例**: 36 ms のフル再構築を 10 ms 周期の制御ループ内で同期実行していた。飛行中に 5 回/秒発火し、墜落直前は時間の 52% が凍結。更新を捨てる方式（上限 5 連続で 1 回だけ再構築）にしたら再構築 80 回→20 回、数値は同等のまま。
- **やり方**: 健全性チェックの発火率を**テレメトリで常時数える**。1 発火あたりのコスト × 発火率 が制御周期の数 % を超えたら設計を見直す。「捨てる」→「上限付きで再計算」の順に段階を作る。
- **出典**: docs/ai/decisions/20260910_sr2_bad_c_rebuild_storm.md
- **汎用度**: 高

## 「戻せば飛ぶ」の前に、戻す先が本当に安定だったのかを同じ指標で測り直す
- **主張**: 変更後に失敗が続いたとき「以前の版へ戻す」は正当な退避だが、**戻す先の版を、失敗を測ったのと同じ指標で再評価**してから決める。以前の版が「安定だった」のではなく「たまたま余裕側に倒れていた」だけのことがある。
- **理由**: 記憶に残る「飛べた」は、短い成功の印象で、その版が抱えていた欠陥（今回は 50 Hz ディザ・NaN 固着・限界モードの存在）は印象に残らない。戻すと、直した欠陥まで全部戻る。加えて、新しく見つかった独立の欠陥（今回は推定器の発散）は旧版でも同じように起きるので、戻しても失敗率は思ったほど下がらない。
- **やり方**: (1) 失敗を 1 件ずつ直接原因に分解し、「戻せば消える件数」を数える。(2) 旧版の「良さ」を測定可能な量（今回は角度ゲインと角速度ゲイン）に還元し、新版でそれを再現できるか確かめる。再現できるなら戻さず A/B する。再現しても新版だけ落ちるなら、そこで初めて旧版へ戻す実験に価値が出る。
- **出典**: docs/ai/decisions/20260910_v5_three_crashes_and_revert_question.md
- **汎用度**: 高

## 検知器の閾値は「壊れた例」だけでなく「正常だった全ログ」で誤発火率を測ってから決める
- **主張**: 異常検知の閾値を「異常事例で発火する値」から決めてはいけない。**正常に動いていた全記録**に同じ検知器をオフラインで当て、誤発火が 0（または許容数）になる値を先に確かめる。
- **理由**: 異常時の残差は大きいので、ほとんどの閾値で「検知できる」。問題は正常時の残差の裾で、それは異常事例だけ見ていては分からない。今回、直感で置いた 3 deg/s は飛べていた飛行で 2-5 回誤発火し、5 deg/s で 0 になった（検知時刻はほぼ変わらず）。
- **やり方**: 検知式をそのまま Python 等で再現し、全ログに対して「飛行中の誤発火数」「異常事例の検知時刻」を閾値ごとに表にする。**発火の副作用が小さい設計**（今回はバイアス状態のみリセット、姿勢に段差なし）にしておくと、閾値の選択に余裕が出る。

- **見分け方**: (1) 指令と応答の**振幅比 ≈ 1 なのに相関が低い** → 帯域不足。(2) 指令トルクが誤差に比例せず頭打ち → 飽和か「レート参照 0 への減速」か。制約の活性度（box・双対変数）を見れば区別できる。活性でなければ後者で、これは設計どおりの挙動。

## 帯域を上げる変更と、むだ時間補償は「組」で動かす

- **主張**: 制御が効いている状態のログでは、入力（操作量）が出力の関数になっているため、
  入出力比は対象ではなく**制御器の逆**や雑音の形を測ってしまう。対象のゲインが欲しいなら、

  「実測/モデル比」は 1/X 倍になるはず。**ならなければ、その推定量は対象を測っていない。**
  実例では推力係数を 28 % 変えた 2 便が同じ比 2.2 を返し、それまでの「モデルが 2 倍過小」という

## 状態機械の表示ルーチンには必ず `else` を置く — 「どの枝にも当たらない」が正常表示に化ける
- **主張**: 状態に応じて LED・画面・ログを切り替える if-else チェーンには、**必ず最後に `else` を置き、
  「未知の状態」を専用の目立つ表示にする**。`else` が無いと出力デバイスは前の値を保持し、
  **異常が「直前の正常表示」として見える**。これは無表示より危険で、原因究明を何時間も遅らせる。
- **理由**: 状態が増えるのは表示ルーチンより先に状態機械側であり、追随漏れは必ず起きる。
  実例では状態 4 と、2 つの状態変数の特定の組み合わせの 2 か所に枝が無く、
  機体は「正常色のまま動かない」という最も紛らわしい見え方をした。
- **併せて**: しきい値で状態を決めるなら**デッドゾーンを残さない**。
  `if (x < 200) A; else if (x > 500) B;` は 200-500 で**変数を書かない**ので前の値が居座る。

- **汎用度**: 高

## 「使わなくなったモード」は分岐だけ消さず、その分岐が担っていた**書き戻し**まで確認する
- **主張**: あるモードを使わなくなって分岐を消すとき、その分岐が「毎周期デフォルト値を書き直す」役割も

## 外乱が「状態そのもの」でなく「状態の積分」に比例していないか確かめる
- **主張**: 未説明の力・トルクを回帰するとき、状態 x だけでなく **∫x dt** も説明変数に入れる。
  x だけで R² が出ないのに ∫x dt で一気に上がるなら、原因は**モデルに無い低次の状態**（速度・位置など）である。
- **理由**: 姿勢だけ／角度だけのモデルは、傾き続けた結果として生じる速度の効果を持たない。
  実例では傾き θ 単独の R² が 0.001-0.024 だったのに ∫θdt を足すと 0.13-0.47 になり、
  「傾けるほど戻される（速度安定）」という、それまで「ゲインが足りない」と誤解していた現象の正体が決まった。
- **効く場面**: 「最初は追従するのに、保持しているとじわじわ戻る」という症状。
  これは**ゲインの問題に見えて積分器の問題**である。比例ゲインをどう振っても解けない。

- **汎用度**: 高

## 1 つのノブが 2 つの指標を同じ比で動かすなら、そのノブでトレードオフは調整できない
- **主張**: 「剛性」と「相対減衰」のように独立に効いてほしい 2 指標が、あるノブで**同じ比率で**動くなら、
  そのノブは設計自由度を 1 つも与えていない。**別の構造（積分項、フィードフォワード、状態追加）が要る。**
- **見分け方**: ノブを振って 2 指標の**比**をプロットする。比が平らなら無力。実例では
  入力重みを 1.6 倍にしても「率/角」は 0.25→0.29 s しか動かず、静的ゲインだけが半分になった。

## 積分（トリム）は「入力の参照」ではなく「出力の目標」側に入れる
- **主張**: 最適化ベースの制御器に積分作用を足すとき、**入力の参照 u_ref をずらす**のではなく
  **状態の目標 x_ref をずらす**。前者は入力コストの重みを通してしか効かないので、
  状態コストが支配的な設計では**オプティマイザが「打ち消すべきずれ」として潰してしまう**。
- **理由**: コストが `(x-x_ref)^T Q (x-x_ref) + (u-u_ref)^T R (u-u_ref)` なら、
  u_ref の効きは R/Q 比に比例する。実例では Q が支配的な軸で、剛性から 12 deg 相当のはずのトリムが
  0.29 deg しか動かず、R が相対的に大きい別の軸だけ期待どおり効いた。**軸ごとに効き方が違うのが罠。**
  x_ref 側なら比に依存せず、「そこへ行け」という指示がそのまま通る。
- **検算**: トリムを入れたときの定常変化が、静的剛性から予想される量と一桁合うかを必ず確かめる。
  合わなければ入れる場所が間違っている。
- **出典**: docs/ai/decisions/20260911_attitude_integral_trim_via_xref_shift.md
- **汎用度**: 高

## 積分の「効かせる帯」を切らないと、操縦のステップで巻き上がって行き過ぎが増える
- **主張**: 積分は**誤差が小さいときだけ**動かす。大きな誤差（＝操縦者が意図的に出した大舵）まで積むと、
  ステップ応答の行き過ぎが増え、積分を入れた目的と逆の不満を生む。
- **理由**: 積分の仕事は「小さな定常のずれを消すこと」であって大舵の補助ではない。
  実例では帯を 25 deg にすると外乱ゼロでも行き過ぎが 0 % → 16 % に増え、
  8 deg に狭めると 9 % に戻った（外乱がある条件では据え置きか改善）。
- **帯の決め方**: 実測の定常誤差の 2-3 倍。それ以上広げると操縦入力を拾い始める。
- **出典**: docs/ai/decisions/20260911_attitude_integral_trim_via_xref_shift.md
- **汎用度**: 高

## 積分器には必ずリーク（減衰）を入れる — 「上限に張り付いたまま」は消せない外乱の証拠であり、害にしかならない
- **主張**: 積分項は `trim *= (1 - dt/τ_leak)` のような緩い減衰を持たせる。上限クランプだけだと、
  **積分で消せない外乱に当たったとき上限に張り付いて戻らなくなる。**
- **理由**: 張り付いた積分はもう誤差を消しておらず、**「指令から一定量ずれた目標を追い続ける」だけの存在**になる。
  実例では姿勢トリムが上限 6 deg に達した後もずっと張り付き、実効目標が操縦者の指令から 5 deg ずれたままになった。
  リークがあれば「釣り合う所」に落ち着き、消せない分は素直に定常誤差として残る（そのほうが読める）。
- **診断としても使える**: **上限張り付きが続く＝その外乱は定常ではない**、という一次情報になる。
  ログに積分値そのものを必ず出すこと。出していないと、この判定ができない。

- **汎用度**: 高

## 抑制機構（リーク・デッドバンド・クランプ）は「効いている軸」にだけ掛ける
- **主張**: 巻き上がり対策として入れる機構は、**実際にその症状が出ている軸/経路にだけ**適用する。

- **理由**: 実例では、張り付いていたのは 1 軸だけなのにリークを全軸共通にしたところ、

## 周期カウンタの折り返しを `==` で書かない
- **主張**: `if (cnt == PERIOD) cnt = 0;` は、そのカウンタが**他の経路から別の値を持ち込まれ得る**なら必ず `>=` にする。共有される状態なら、持ち主が変わった時点で明示的にリセットする。
- **理由**: 完全一致の折り返しは「その値をちょうど通過する」ことに依存している。上限より大きい値で入ってきた瞬間に条件が永久に成立せず、カウンタは型の最大値まで暴走する。その間、同じカウンタを見ている `cnt == 0` のような**出力側の条件も一切成立しない**ので、機能が「静かに」死ぬ。ログにもエラーにも出ない。
- **付随する教訓**: 「どの分岐に入ったか」を計装しても、**分岐の中で副作用が実行されたか**は分からない。表示・出力の不具合では**出力そのものの発生**を観測対象にすること。
- **出典**: docs/ai/decisions/20260919_led_blink_counter_runaway.md
- **汎用度**: 高
