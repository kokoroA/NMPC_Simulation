# 0831_v3.csv 解析 — 「飛んでいる時間が長いほど操作性が落ちる」の原因

- **ログ**: `Benzen_NMPC/tools/0831_v3.csv`（10 Hz、155 点 / 17.6 s、NMPC 稼働 86 点）
- **図**: `plots/0831_v3_analysis.png`, `plots/0831_v3_cycles_vs_error.png`
- **この版の変更**: `R_u` 28 → **120**、周期フル再構築を `u_hover < 0.30` に限定
- **前回**: [`20260831_nmpc_flight_v1_gain_tuning.md`](20260831_nmpc_flight_v1_gain_tuning.md)

## 0. 結論

**ご指摘のとおりです。周期フル再構築を飛行中に止めたことが最有力の原因です。**
ただし**このログだけでは因果を確定できません**（§2）。次の飛行で 1 定数だけ変えれば決着します。

### 0-1. `R_u = 120` は明確に効いた

| | phi rms | theta rms | p rms | q rms | duty ばらつき | 飽和 | 飛行時間 |
|---|---|---|---|---|---|---|---|
| **v1**（R_u=28） | 15.71° | 10.25° | 71.7 | 95.5 | 0.688 | 19 回 | 1.5 s |
| **v3 前半**（R_u=120, cycles≤408） | **7.15°** | **2.24°** | **19.5** | **13.3** | **0.216** | **1 回** | — |
| v3 後半（cycles>408） | 12.78° | 10.88° | 47.7 | 36.5 | 0.621 | 34 回 | — |

**前回の 4 Hz 発振は消え、飛行時間は 1.5 s → 7.1 s に伸びました。** ゲインを下げた判断は正しかった。

### 0-2. そのうえで、時間とともに単調に悪化している

`cycles_since_reset`（フル再構築からの経過周期）で区切ると:

| cycles | 経過 [s] | 姿勢誤差 rms | duty ばらつき | 飽和 |
|---|---|---|---|---|
| 0–150 | 8.6–10.2 | **4.48°** | 0.110 | 0 |
| 150–300 | 10.3–11.4 | 8.50° | 0.164 | 0 |
| 300–450 | 11.8–13.2 | 8.09° | 0.456 | 1 |
| 450–600 | 13.3–14.7 | **17.34°** | 0.671 | 14 |
| 600–800 | 14.8–16.4 | **18.04°** | 0.571 | 20 |

- 相関 `cycles` vs 姿勢誤差 **+0.704**、vs 角速度 **+0.667**
- **指令のばらつきが 0.02 → 0.84 へ単調に増加**し、cycles≈450 から飽和が出始める
- 後半の振動は約 1 Hz。v1 の 4 Hz 発振（ゲイン過大）とは**別の性質**

## 1. 何が起きているか — 具体的な機構

このログで**確認できた事実**:

| 項目 | 値 | 意味 |
|---|---|---|
| `cnt_rst_period` | **1**（t=16.60、着地後） | 飛行中は周期再構築ゼロ。**ゲートは意図どおり動いた** |
| `cnt_sr2_c` / `cnt_rst_after_sr2` | **1**（t≈8.7） | SR2 健全性異常は **888 周期で 1 回しか発火していない** |
| `cnt_tr1` / `cnt_tr1_ok` / `cnt_tr1_skip` | 888 / 888 / **0** | **TR1 は 888 周期すべてで適用され、1 度もスキップされていない** |
| `iter_us` 最大 / `loop_us` 最大 | 8965 µs / 10867 µs | **58 ms の停止は飛行中から消えた**（修正は効いている） |

`rti::secant_min_norm = 1.0e-6f` は「小さすぎる割線対では更新をスキップする」ためのガードですが、
**`cnt_tr1_skip = 0` は、このガードが一度も働いていないことを示しています。**

ホバー中は機体がほとんど動かないため、割線対 (s, y) は**ノイズと同程度に小さい**はずです。
その状態で **888 周期連続してランク 1／ランク 2 更新を float32 で積み上げれば、
`Su` と `H` が真値から離れていくのは自然**です。
そして SR2 の健全性チェックはそれを 888 周期で 1 回しか検出できていません。

**周期フル再構築は、まさにこの漂流を洗い流すために置かれていたもの**（`nmpc.cpp` の
「差分更新の数値誤差累積対策」というコメント）で、私はそれを飛行中に止めてしまいました。

## 2. ⚠ このログだけでは因果を確定できない

`cycles` と経過時間は **t=8.99 以降ずっと同一直線上**にあります（再構築が 1 回も入らないため）。

```
相関 cycles vs 姿勢誤差 = +0.704
相関 経過時間 vs 姿勢誤差 = +0.713   ← ほぼ同じ
```

したがって「Hessian の漂流」と「時間とともに増える他の要因」（電池電圧の低下、
機体が離陸点から離れて操縦が難しくなる、地面効果から抜ける、操縦者の疲労）を
**このデータでは切り分けられません。**

**次の飛行で決着します（§3 Step 1）。**

## 3. 対策

### Step 1 — 次の飛行：定数 1 つだけ戻す（**推奨**）

```cpp
// nmpc_params.hpp  namespace rti
constexpr float rebuild_max_u_hover = 1.0f;   // 0.30f → 1.0f（飛行中も周期再構築を許可）
```

`reset_period = 100`、`R_u = 120` はそのまま。**これは決定的な実験であると同時に、そのまま対策にもなります。**

**なぜ今なら 58 ms の停止に耐えられる可能性が高いか:**

v1 で 58 ms が危険だったのは、**その時すでに 100–200 deg/s で発振していたから**です（58 ms × 150 deg/s ≈ 9°）。
v3 前半の角速度は **q rms 13 deg/s** まで下がっています。この状態なら
**58 ms の停止は約 0.8° の漂流**にしかなりません。

| 結果 | 解釈 |
|---|---|
| 長く飛んでも劣化しない | **仮説確定。これで対策完了**（1 秒ごとの 58 ms は許容できていた） |
| 劣化は消えたが 1 秒ごとにガクつく | Step 2 へ |
| 劣化が変わらない | 原因は Hessian の漂流ではない。電池・操縦・地面効果を疑う |

### Step 2 — ガクつきが出た場合：機体が静かな時だけ再構築する

```cpp
// control.cpp 側で「今は止まっても安全か」を判定して渡す
const bool calm = (fabsf(Wp-Pbias) < 1.0f) && (fabsf(Wq-Qbias) < 1.0f) && (fabsf(Wr-Rbias) < 1.0f)
                  && !any_motor_saturated;   // 1.0 rad/s ≈ 57 deg/s
```

`nmpc_step` に渡し、`period_due` の条件に加えます。
**58 ms の穴を「穴が開いても影響が小さい瞬間」に寄せる**のが狙いです。
`reset_period` を少し伸ばして（例 150）、静かな瞬間を待つ余裕を作るとより確実です。

### Step 3 — 根治：フル再構築のコストを下げる

フル再構築は `H = Suᵀ Q̄ Su + R̄`（102×102 を 85×102 から）と LLT 分解が支配的で、
**コストはおよそ `N³` に比例**します。

| N | 予測ホライズン | フル再構築（現状 58 ms から換算） | 備考 |
|---|---|---|---|
| 17（現行） | 0.17 s | 58 ms | 制御周期の 6 倍 |
| 12 | 0.12 s | **約 20 ms** | 2 周期 |
| 10 | 0.10 s | **約 12 ms** | ほぼ 1 周期 |

**`N` を下げれば `iter_us`（現在 8.5 ms、`loop_us` は 10.3 ms で予算超過）も同時に下がります。**
「10 ms 以内に収める」という未解決課題と**同じノブ**です。
`repository_rules.md` が「`N` は計算時間とメモリの両方に効く最重要ノブ」と書いているのはこのことです。

⚠ ホライズンを縮めると制御性能も変わります。**変えたら必ず実測し直すこと。**

### Step 4 — SR2 健全性チェックが漂流を検出できていない

**888 周期で 1 回しか発火していません。** 本来はこれが「必要になったときだけ再構築する」仕組みのはずで、
うまく働けば周期再構築そのものが要らなくなります。

- `secant_min_norm = 1.0e-6f` を上げ、**ノイズ同然の割線対では更新をスキップする**
  （`cnt_tr1_skip = 0` は現在の閾値が一度も効いていない証拠）
- 健全性の判定条件を見直す

**まず計装から。** `|s|`, `|y|`, `H` の対角の最小/最大などをテレメトリに出せば、
漂流を直接観測できます。今は「悪化した」ことは分かっても「何が壊れたか」が見えません。

### Step 5 — 構造的な解（要メモリ検討）

**core0 でフル再構築を行い、完成したら core1 とアトミックに差し替える。**
core1 は再構築中も TR1/SR2 で 100 Hz を回し続けるので、**停止がゼロになります。**

⚠ ただし `Su`・`H`・LLT の**シャドウ領域が必要**です。`H`+LLT だけでも約 83 kB。
現在 bss は 402 kB / SRAM 520 kB、core0 スタック 32 KB を足すと **残りは約 86 kB**。
**成立するかは実測しないと分かりません。先に Step 1〜3 を試すべきです。**

## 4. 推奨する順序

| # | 内容 | 変更量 |
|---|---|---|
| **1** | `rebuild_max_u_hover` を 1.0f に戻して飛ばす | **定数 1 つ** |
| 2 | 効果が確認できたら、`|s|`/`|y|`/`H` 対角を計装に追加 | 小 |
| 3 | ガクつくなら「静かな時だけ再構築」 | 中 |
| 4 | `N` を 12 へ下げて再構築コストと `loop_us` を同時に削る | 中（要再チューニング） |
| 5 | `secant_min_norm` と健全性判定の見直し | 要計装 |

**1 回に 1 つだけ変えてください。** 今回 `R_u` とゲートを同時に入れたため、
「R_u が効いた」ことと「ゲートが悪さをした」ことが混ざって見えています。
