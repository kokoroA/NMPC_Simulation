# 0904_v11 分析 — 空中でのモータ停止は「姿勢の脱出条件」ではなく受信機フラグ（FS_RX_LOST）

- **対象ログ**: `Benzen_NMPC/tools/0904_v11.csv`（10 Hz テレメ, 626 行, 約 67 s）
- **重み**: `Q_phi = Q_theta = 150`, `Q_p = Q_q = 20`, `Q_r = 40`, `R_u = 120`, `N = 14`
- **図**: `Benzen_NMPC/tools/plots/0904_v11_failsafe.png`

---

## 1. 結論（先に答え）

**発動したのは姿勢・角速度の脱出条件ではない。`failsafe = 1 = FS_RX_LOST`（受信機フラグ）である。**

したがって **「姿勢 60° / 角速度 300 deg/s のしきい値を厳しく（＝広く）する」対応は無意味**。
その 2 つは今回一度も触れていないし、飛行中ずっと大きな余裕があった。

| 量 | 飛行中の最大 | しきい値 | 使用率 |
|---|---|---|---|
| `\|phi\|` | 18.6 deg | 60 deg | 31.0 % |
| `\|theta\|` | 12.4 deg | 60 deg | 20.7 % |
| `\|p\|` | 95.1 deg/s | 300 deg/s | 31.7 % |
| `\|q\|` | 55.1 deg/s | 300 deg/s | 18.4 % |
| `\|r\|` | 79.1 deg/s | 300 deg/s | 26.4 % |

**発動した瞬間（seq 7732, t = 67.1 s）の姿勢は φ = +1.5°, θ = −2.6°、角速度は p = 11.3, q = 11.7, r = 2.0 deg/s。**
つまり**ほぼ水平・ほぼ静止**の状態でモータが切れた。姿勢由来ではありえない。

発動後の φ, θ, q が増えているのは、**モータが止まった結果として機体が落ち始めた**ためであり、原因ではない。

## 2. 何が起きたか

`control.cpp` `failsafe_check()` の (1) が成立した。

```cpp
const uint16_t sbus_flags = Chdata[16];      // = sbus_data[23]
if (sbus_flags & (SBUS_FLAG_FAILSAFE | SBUS_FLAG_FRAME_LOST))   // 0x08 | 0x04
    cause = FS_RX_LOST;
```

`Chdata[16]` は `radio.cpp:149` で**毎フレーム上書きされる生のフラグバイト**で、
カウンタもデバウンスも無い。そして `failsafe_check()` は**ラッチ式**（`Arm_flag != 2` まで解除しない）。

**結果として「1 フレームだけビットが立った」だけで、飛行中に永久にモータが切れる。**

### 0x04（FRAME_LOST）は「異常」ではなく「日常」

SBUS のフレーム周期は 7 ms（高速）または 14 ms。受信機は**1 フレーム取りこぼしただけで 0x04 を立てる**。
これは電波環境が少し混んだだけで普通に起きる。「機体が操縦不能になった」という意味ではない。

一方 0x08（FAILSAFE）は「送信機を見失って受信機が自分の failsafe 動作に入った」という
本物の信号であり、これは即座に止めてよい。**この 2 つを同じ扱いにしているのが設計上の誤り。**

さらに、**本物のリンク断は既に (2) `FS_RX_TIMEOUT`（200 ms 無受信）が捕まえる。**
0x04 で即停止する必要は最初から無かった。

### 電波環境が実際に悪化していた（傍証）

テレメトリ（Wi-Fi UDP）の欠測率を 10 s ごとに見ると、**停止直前の 10 s だけ突出している**。

| 時間帯 | 欠測率 |
|---|---|
| 0–10 s | 8.0 % |
| 10–20 s | 2.0 % |
| 20–30 s | 4.2 % |
| 30–40 s | 6.6 % |
| 40–50 s | 3.1 % |
| 50–60 s | 2.0 % |
| **60–70 s** | **16.1 %** |

停止の直前には **0.70 s のテレメトリ欠測**（seq 7591 → 7671）があった。全体の受信率は 93.0 %。

⚠ **Pico 2 W の Wi-Fi AP は 2.4 GHz で、RC リンクと同じ帯域を使っている。**
自機の Wi-Fi が自機の受信機を潰している可能性がある。これは推測であり未確認。

つまり **0x04 が立ったこと自体は「誤検知」ではなく、電波環境の悪化を正しく反映していた可能性が高い。**
問題は「1 フレームの取りこぼしに対して、空中で永久にモータを切る」という**反応の激しさ**の方である。

## 3. 対策案

### A. 受信機条件を 2 つに分ける（本命）

| ビット | 意味 | あるべき対応 |
|---|---|---|
| `0x08` FAILSAFE | 送信機を見失った（本物） | **即ラッチ**（現状のまま） |
| `0x04` FRAME_LOST | 1 フレーム取りこぼし | **単発では発動しない。** カウントするだけ |

`0x04` に対しては、実質的な保護は既に `FS_RX_TIMEOUT`（200 ms 無受信）が担っている。
どうしても 0x04 も見るなら、**「連続 N フレーム（≒100–200 ms 相当）立ちっぱなし」を条件にする**。
単発カウントはテレメトリに出して、後からリンク品質として読めるようにする。

原因コードも分離する（`FS_RX_FAILSAFE` / `FS_RX_FRAMELOST`）。
**今のログでは 0x04 と 0x08 のどちらだったか区別できない。これが今回の調査を長引かせた。**

### B. 計装（次の飛行の前に必ず入れる）

- テレメトリに **`Chdata[16]` の生値**と **frame-lost の累積カウント**を出す。
- 0x04 / 0x08 の発生頻度が分かれば、A のしきい値を実測で決められる。

### C. 電波（ハード側）

- **Wi-Fi テレメトリを切って同じ飛行をしてみる。** これで frame-lost が消えるなら原因が確定する。
- 受信機アンテナと Pico 2 W の距離・向きを離す。

### D. 「空中で全モータ即停止」という応答自体の再考（別課題）

受信機ロストに対して高度を持ったまま全モータを切るのは、**必ず墜落**を意味する。
本来は「姿勢水平・スロットル緩やかに絞る」自動降下の方が被害が小さい。
ただしこれは設計変更が大きいので、まず A と B を先に片付けること。

## 4. しきい値を「厳しくする」件への回答

**姿勢 60° / 角速度 300 deg/s は、むしろ広すぎるくらいで、今回まったく関係していない。触らないこと。**

ユーザの体感「大きい目標値が入って一瞬姿勢が崩れたくらいで止まってほしくない」は正しい要求だが、
**今回止めたのはそれではない**。指令スケールは ±54°、実際の姿勢は最大 18.6° で、
脱出条件の 1/3 にも届いていない。ここを広げると、本当に姿勢が破綻したときの保護だけが失われる。

なお加速度 150 m/s²（`FS_OVERG`）も今回発動していない（`failsafe = 5` は一度も出ていない）。

⚠ ただし `OverG_flag` には別の注意点がある。`control.cpp:2301` で立ち、
`control.cpp:701` の 1 か所でしか落とされない。**一度立つと落ちるまでラッチに近い挙動**になるので、
将来しきい値を下げるときはクリア条件も併せて見直すこと。

## 5. 副次的な所見（重み `Q_r = 40` の評価）

### 良くなった点 — ヨーは直った

| 指標 | v6 (`Q_r=20`) | **v11 (`Q_r=40`)** |
|---|---|---|
| ヨー追従 振幅比 | −1.066 | **+1.152** |
| ヨー追従 相関 | +0.21 | **+0.80** |
| ヨードリフト（r 平均） | +21 deg/s | **+5.2 deg/s** |

**`Q_r` を上げる方針は正しかった。** ドリフトは 1/4 になり、指令にきちんと追従するようになった。

### 悪くなった点 — ロール・ピッチが痩せ、飽和が増えた

| 指標 | v6 | **v11** |
|---|---|---|
| Δu の yaw 分散比 | 29.3 % | **41.5 %** |
| Δu の roll 分散比 | 18.3 % | 16.5 % |
| Δu の pitch 分散比 | 7.2 % | 15.5 % |
| duty 飽和（0.95 到達）率 | 1–5 % | **23.2 %** |
| roll 追従 振幅比 | — | 0.424 |
| pitch 追従 振幅比 | 0.291 | 0.517 |

**ヨーが再び Δu の 4 割を食っている。** v1（84.7 %）ほどではないが、`Q_r = 20` のときより増えた。
ヨーの実際の指令量（`ΣkS·u` 平均 −0.153）は最大差動 ±2.85 に対して**わずか 5.4 %**なので、
**ヨー軸が飽和しているのではなく、ヨーを合わせるために余計に duty を振っている**状態。

飽和 23.2 % は放置できない。内訳は FR 10.0 %, RR 9.1 %, ML 8.4 %, MR 7.1 % に対し
**FL 0.7 %, RL 0.2 %** と偏っている。`u_base` 平均 0.627 / 最大 0.832 で、
**上方向に 0.118 しか残っていない**のが根本にある（推力マージン不足）。

### 次の 1 手（提案・未検証）

`Q_r = 40` は残す。飽和の原因はヨーの重みではなく**推力マージン**なので、
`Q_r` を下げるとヨードリフトが戻るだけで飽和は大して改善しない。
先に **ホバー duty を下げる**（機体重量・`T_max`・`mass` の整合）方を潰すべき。

⚠ 未解決のまま持ち越している項目: `mass = 0.35` に対し実測 ≈0.383 kg、
`T_max = 1.04` に対し同定値 0.79–0.82、`Iz = 3.00e-3` の出所未確認、RL モータの Δu 分散偏り。
