# 0909_v1 / v2 飛行解析 — 墜落はロール逸脱、T_max は 0.81 で飛んでいない、モータ固着は NaN

- **ログ**: `0909_v1.csv`（10 Hz, 418 点, 45 s。**墜落**）/ `0909_v2.csv`（10 Hz, 86 点）/
  `0904_100Hz_v5.csv`（100 Hz, 852 行 = 8.5 s）
- **図**: `Benzen_NMPC/tools/plots/0909_v1_v2_analysis.png`
- **構成**: F1404 + GEMFAN-3630-3、`T_ref_coe` 0.6 → **0.85**

> `0909_v2.csv` と `0904_100Hz_v5.csv` は **同一飛行**であることを確認した
> （`seq = 100*t + 2359` で平均 `|Δphi|+|Δtheta| = 0.0002 deg`）。

---

## 0. 先に、重要な 3 点

1. **墜落は「ピッチ暴走」ではなく「ロール逸脱」。** `phi_ref` がほぼ 0 のまま `phi` が 140° まで走った。
2. **この飛行は `T_max = 0.81` で飛んでいない。** 100 Hz ログのヘッダは **`T_max = 1.040`**。
   `nmpc_params.hpp` は現在 `0.81f` なので、**書き込みが飛行後か、書き込み漏れ**。
   次に焼くとループゲインが **1.28 倍**になる。**今のピッチとヨーの状態で焼くのは危険。**
3. **disarm 後にモータが一定回転しか出なくなった原因は NaN。**
   duty が NaN になると 400 Hz の NaN ガードが `minimum_duty = 0.1` に置き換えるため、
   **スロットルに関係なく全 6 発が duty 0.1 で回り続ける。** 電源再投入で直るのはこのため。

- **`phi_ref` は 0.1〜1.0° しか出ていない。** それに対し `phi` は +11 → **+140°** へ単調に走った。
- **`theta` は −24° までで収まっている。** ピッチは崩れていない。
- `p` は 246 deg/s に達し、以後 170 deg/s で回り続けた＝**機体は横転した**。

### 破綻の前から出力が全振幅でバタついていた

上表の duty を見ると、**連続する 10 Hz サンプルで 0.000 と 0.950 の間を往復**している
（`t=40.84` FR 0.950 → `40.94` 0.950 → `41.01` **0.000** → `41.12` 0.950 → …）。
これは既知の **50 Hz 毎周期反転チャタリング**
（[`20260904_duty_chatter_50hz_nullspace.md`](ai/decisions/20260904_duty_chatter_50hz_nullspace.md)）が
**飽和限界まで振幅を伸ばした**状態である。100 Hz ログでも**変動の 72 % が 50 Hz 反転成分**
（Δu 反転 rms 0.0832 / 滑らか rms 0.0522、ラグ1 自己相関 −0.66〜−0.39）。

**モータは 50 Hz を追えないので、実際に出るのは 2 サンプル平均だけ。
つまりロール軸の実効的な操作量が失われた状態で、姿勢が崩れた。**

### フェイルセーフは正しく働いた

| 時刻 | 事象 |
|---|---|
| 15.59 s | `failsafe = 4`（角速度 300 deg/s 超）→ 16.21 s に解除（**再アームで解除できている＝先日の修正が機能**） |
| 41.23 s | `failsafe = 3`（姿勢 60° 超。実測 74°）→ モータ停止 |
| 41.68 s | duty が **NaN** に。以降 26 点すべて NaN |
| 42.06 s | `failsafe` 解除（disarm） |

**フェイルセーフは 74° で正しく発火している。** 発火が遅かったのではなく、
**60° に達した時点で既に回復不能な角速度（170 deg/s）が付いていた。**

⚠ 15.59 s に一度 `failsafe = 4` が出ている。**この時点で既に角速度 300 deg/s を超える暴れがあった。**

## 2. モータが一定回転しか出なくなった件（disarm しても直らない）

**原因は NaN。** [`control.cpp:1579`](../program/pico/pico-sdk2/pico-sdk/Benzen_NMPC/control.cpp) の NaN ガード:

```cpp
float minimum_duty = Disable_duty;      // = 0.1
...
if (*duties[i] != *duties[i])           // NaN 判定
    *duties[i] = minimum_duty;          // ← 0.1 に置き換える
```

duty が NaN になると **全 6 発が duty 0.1 に固定**され、その後の出力段は
`common_duty >= Disable_duty` なら `set_duty_*(0.1)` を出す。
**スロットルをいくら上げても一定回転にしかならない**のはこれ。

**なぜ disarm で直らないか。** ログでは墜落直後に姿勢推定が発散している
（`phi = -336.6 deg`, `-333.7`, `-329.6` …）。**姿勢推定が壊れたまま**なので、
再アームしても `x0` が異常 → NMPC が NaN → 同じ状態に戻る。
**電源を抜くと EKF が初期化されるので直る。**

⚠ **`control.cpp` に NaN / 発散に対する保護はこの 1 行しかない**（`isnan`/`isfinite` の使用は 0 箇所）。
姿勢推定にもソルバ状態にも復帰手段が無い。

## 3. `T_max` が申告と違う

| | ユーザ申告 | 100 Hz ログのヘッダ | 現在の `nmpc_params.hpp` |
|---|---|---|---|
| `T_max` | 0.81 | **1.040** | `0.81f` |
| `mass` | — | 0.335 | `0.335f` |

**`mass` は一致し `T_max` だけ食い違う。** つまりソースは編集されているが、
**この飛行のファームには反映されていない**（飛行後に編集したか、焼き漏れ）。

`B_c ∝ T_max` なので、**次に焼くとロール・ピッチ・ヨーすべてのループゲインが
`1.04/0.81 = 1.28 倍`になる。**

⚠ **ピッチが既に発振気味・ヨーが既に 1.4 倍の過剰応答である今、そのまま焼くのは危険。**
`T_max` を下げるなら `R_u` を上げるか `Q` を下げて対で調整すること
（[`20260831_nmpc_gain_too_high_oscillation.md`](ai/decisions/20260831_nmpc_gain_too_high_oscillation.md) と同じ轍）。

## 4. ロール・ピッチ・ヨーの性能（100 Hz, 自由飛行 6.5 s）

| 軸 | 指令 rms | 応答 rms | **振幅比** | 相関 | 誤差 rms | 遅れ |
|---|---|---|---|---|---|---|
| **roll** | 4.18° | 2.94° | **0.704** | +0.56 | 3.53° | 260 ms |
| **pitch** | 5.45° | 5.78° | **1.061** | +0.67 | 4.56° | 400 ms |
| **yaw** | 13.88 deg/s | 19.64 deg/s | **1.415** | +0.87 | — | — |

**ユーザの体感（ロールは良い／ピッチはゲインが高い）は数値と一致する。**

### 周波数で見ると、ロールとピッチは別のモードで暴れている

| 信号 | 全帯域 rms | 0–1 Hz | **1–3 Hz** | **3–6 Hz** | >6 Hz |
|---|---|---|---|---|---|
| `p`（ロールレート） | 19.60 deg/s | 37.2 % | 6.9 % | **34.8 %** | 5.6 % |
| `q`（ピッチレート） | **26.46 deg/s** | 13.2 % | **55.7 %** | 11.1 % | 2.2 % |
| `r`（ヨーレート） | 19.64 deg/s | 81.0 % | 8.4 % | 1.0 % | 1.0 % |

- **ロールは 3–6 Hz**（rms 4.71 deg/s）＝ 既知の**モータ一次遅れ由来の 4 Hz モード**
- **ピッチは 1–3 Hz が 55.7 %**（rms 6.19 deg/s が 3–6 Hz、しかし主峰は 1–3 Hz）
  ＝ **ロールとは別の、もっと遅いモード**。遅れも 400 ms とロール（260 ms）より長い

**ピッチだけ低い周波数で振れている。** 単純な「ゲインが高い」なら
ロールと同じ 4 Hz 帯に出るはずで、そうなっていない。
`Q_theta` を下げるだけでは筋が通らない可能性がある。

### ヨー — 過剰応答が悪化している

| 飛行 | 振幅比 | ドリフト |
|---|---|---|
| v4 (D90S) | 1.074 | +4.8 deg/s |
| v11 (D90S) | 1.152 | — |
| **v5/v2 (GEMFAN)** | **1.415** | **−5.01 deg/s** |

**指令の 1.4 倍回っている。** 一方で

- **ヨーは Δu の 47.8 % を消費している**（roll 30.6 %, pitch 11.1 %, common 10.6 %）
- なのに**実際のヨー差動は最大値の 1.7 % しか使っていない**（`ΣkS·u` 平均 −0.048 / 最大 2.85）

**ヨー軸は飽和していないのに、Δu の半分を食っている。** これは
[`20260904_yaw_starves_roll_pitch.md`](ai/decisions/20260904_yaw_starves_roll_pitch.md) と同じ構図で、
**ピッチが 11.1 % しか使えていない**のはこの取り合いの結果でもある。

⚠ 過剰応答の候補: ① モデルの `Cr = 0.005` が上界の 25 倍で「回しすぎ」方向に働く
（[`20260909_cr_is_not_a_drift_knob.md`](ai/decisions/20260909_cr_is_not_a_drift_knob.md)、+9.8 % 相当）、
② `C_QT` の誤差、③ プロペラ交換による実効ゲイン変化。**①だけでは 1.4 倍を説明できない。**

## 5. `T_ref_coe = 0.85` — スロットルが敏感すぎる

```
T_ref  = 3.7 × スティック割合
u_base = 0.85 × T_ref = 3.145 × スティック割合、0.95 で頭打ち
```

| スティック | `u_base` |
|---|---|
| **20 %** | 0.62（ホバー付近） |
| **30 %** | **0.95（上限）** |
| 100 % | 0.95（変わらない） |

**ホバーから全開までがスティック travel の 10 % しかない。** 上 70 % は完全に無効。
ユーザの「推力がスティックに敏感」はこのとおりである（`T_ref_coe = 0.6` のときは 16 %）。

実測では `u_base >= 0.949` は v1 で 0.7 %、v5 で 0.0 % と**張り付き自体は稀**だが、
**墜落の最終局面（41.43–41.53 s）では `u_base = 0.950` に達しており、
その瞬間 Δu の上側余裕はゼロ＝姿勢制御の権限が完全に消えていた。**

## 7. 次にやること（優先順）

1. **`T_max` を焼く前に、ピッチとヨーを落ち着かせる。** そのまま焼くと全軸 1.28 倍。
2. **50 Hz チャタリングの原因を潰す。** 墜落時に全振幅まで育っており、
   これが実効的な操作量を奪っている。**プロペラを外して固定し、スティック一定で 100 Hz ログを取る**
   （ベンチ加振モードが実装済みなので `admm_max_iter` 2 → 4 の効果もそこで見られる）。
3. **NaN からの復帰手段を入れる。** 現状 `isnan` の使用は 0 箇所。
   最低限、姿勢推定の発散検知と再アーム時の EKF 初期化。
   **今のままだと毎回バッテリを抜くことになる。**
4. **ピッチの 1–3 Hz モードを切り分ける。** ロールの 4 Hz とは別物なので、
   `Q_theta` を下げる前に何が振れているのかを特定する。
5. `T_ref_coe` を下げてスロットル分解能を戻すか、`T_ref` 側の係数（0.5）を見直す。

⚠ 未解決の持ち越し: `Cp/Cq/Cr` 未同定、`Ix/Iy/Iz` が `NMPC_REPORT.md` と 3.4–3.9 倍食い違い、
`mass = 0.335` の実測根拠、周期フル再構築 38 ms。
